CMake Tutorial

前言

  当我们只需要编译一个cpp文件时，在macOS系统中可以直接使用g++进行编译，运行生成的可执行文件即可。（对应c语言的是gcc）

  我们平时在编写程序时通常只有一个源文件，所有的代码都写在这个文件中，直接编译即可；但是在实际的项目中，通常会有多个模块，而每个模块又由多个源文件、头文件、第三方库组成，这时候再去一个个的编译效率就会低很多，而构建所做的就是自动化完成编译、链接、打包的过程，我们平时使用的ide都内置了构建系统。

一、CMake

   CMake 全称为 Cross Platform Make，从名字中就能看出来这是一款跨平台的构建工具，它是不自带编译工具的，是比 Makefile 更高层次的构建工具， 相当于一个 CMake 配置文件就可以自动生成 Makefile文件（或是对应操作系统的配置文件）

操作系统 常用编译器（C/C++）
Linux GCC（gcc/g++）：开源且默认；
Clang（clang/clang++）：兼容性好。
macOS Clang：Xcode 内置；
GCC：可通过包管理器安装（非默认）。
Windows MSVC（Microsoft Visual C++）：VS内置；
MinGW/GCC：跨平台兼容。

  随后我们即可通过这个 CMakeLists.txt 文件生成目标平台下的原生工程，如Windows下的Visual Studio工程，macOS下的Xcode工程，Linux下的Makefile工程，这个过程在cmake中叫做配置（config）,这个过程本质上解决了跨平台编译问题。

CMake 工作流程回顾：编写 CMakeLists.txt → 运行 cmake 配置生成 Makefile（或其他构建文件）→ 运行 make 编译链接生成可执行文件 → 运行程序。
两阶段的设计是 CMake 跨平台的关键：配置阶段处理平台差异，构建阶段执行实际的编译链接。

  我们运行cmake，它会读取 CMakeLists.txt 配置文件，根据项目结构、编译选项等信息，自动生成适用于当前系统的Makefile（或其他构建系统文件）

（二）、工程中的应用(多文件)

我们先来学习一下头文件的使用方法。

1.头文件保护

用于防止头文件被重复包含导致的编译错误

2. 只放声明，不放定义

头文件的核心作用是声明接口，而非实现代码，否则可能导致 “多重定义” 错误。

✅ 允许的内容（声明）：

  • 函数声明（int add(int a, int b);）
  • 类 / 结构体声明（class MyClass; 或完整类定义，类内可包含函数声明）
  • 变量声明（需加extern，如 extern int global_var;）
  • 宏定义（#define MAX 100）
  • 模板声明或定义（模板必须在头文件中实现，特殊情况）

❌ 不允许的内容（定义，除非有特殊处理）：

  • 普通函数定义（除非用inline修饰）写在相应源文件中
  • 非extern变量定义（如 int global_var = 0; 会导致重复定义）
  • 可执行代码（如独立的for循环、cout语句等）

3. 好处

  • 编译速度
    如果把实现都写在 .h 文件，任何修改这个文件，所有 #include 它的文件都要重新编译
  • 代码组织
    • .h 文件：快速浏览类的结构和接口
    • .cpp 文件：看具体实现细节

（三）、外部构建（Out-of-source Build）

  在前面的示例中我们直接在项目根目录运行 cmake .，这会污染源码目录，让目录里充斥着 CMakeCache.txt、CMakeFiles/、Makefile 等大量构建产物，不利于版本管理也容易跟源文件混淆。

（五）、链接库

  CMake 中的库分为静态库（Static Library）和动态库（Shared Library）两种：

类型 关键字 产物（Linux） 特点
静态库 STATIC libxxx.a 在链接时被拷贝进可执行文件，独立运行但体积大
动态库 SHARED libxxx.so 在运行时动态加载，体积小但部署时需带上 .so 文件

target_link_libraries 同样支持 PUBLIC / PRIVATE / INTERFACE 三种可见性：

  • PRIVATE：仅当前目标使用，不传递给依赖它的目标
  • INTERFACE：当前目标不使用，但传递给依赖它的目标
  • PUBLIC：相当于 PRIVATE + INTERFACE，既自己用又传递

静态库 vs 动态库如何选择？

  • 静态库：适合最终交付独立运行的场景（如命令行工具、嵌入式），无需带一堆 .so/.dll
  • 动态库：适合多处复用、需要热更新、运行时按需加载的场景（如插件系统、游戏 Mod）
  • 简单记忆：库大且少 → 静态；库小且多 / 需要共享 → 动态

初学者最易踩的坑：target_link_libraries 中漏写 PUBLIC/PRIVATE/INTERFACE 时，CMake 会默认按旧式语法处理，可能造成依赖泄漏。新项目务必显式写明可见性。

（八）、CMake CLI 常用命令

为什么推荐 cmake --build 而不是直接 make？ 因为 cmake --build 是跨平台的 —— 它会自动调用当前生成器的构建工具（Linux 下是 make，Windows 下是 msbuild，安装了 Ninja 时是 ninja），让构建命令无需关心平台差异。这也是前端 IDE（CLion、VS Code）内部使用的方式。

（九）、最佳实践

1. 永远使用外部构建
不要在源码目录直接运行 cmake .，养成 mkdir build && cd build && cmake .. 的习惯。

2. 现代写法优先使用 target_ 系列命令*
旧风格的全局命令（include_directories、add_definitions、link_libraries）影响整个项目及其子目录，容易造成污染。现代 CMake 推荐使用带 target_ 前缀的命令，作用域明确：

3. 显式指定 C++ 标准
使用 target_compile_features(main PRIVATE cxx_std_17) 比全局 set(CMAKE_CXX_STANDARD 17) 更精确。

4. 不要滥用 GLOB
如果一定要用 file(GLOB)，务必加上 CONFIGURE_DEPENDS，否则新增文件不会触发重新配置。

5. 保持 CMakeLists.txt 简洁
复杂逻辑拆到子目录的 CMakeLists.txt 中，根目录只做顶层组织。

总结

  CMake 的内容远不止于此（还有生成器表达式、自定义命令、测试集成 CTest、打包 CPack 等高级特性），但掌握本文的内容已经足以应付日常项目中的绝大多数构建场景。核心知识点回顾：

  • CMakeLists.txt 是 CMake 的配置文件，描述如何构建项目
  • 工作流程是 cmake（配置）→ make / cmake --build（构建）→ 运行
  • 始终使用外部构建（独立的 build 目录）保持源码目录干净
  • 多模块项目通过 add_subdirectory + add_library + target_link_libraries 组织
  • 使用 find_package 引入第三方库
  • 现代写法优先使用 target_* 系列命令，避免全局污染

  更深入的内容推荐阅读官方文档：CMake Tutorial 以及经典开源项目的 CMakeLists.txt 写法（如 JSON for Modern C++、OpenCV）。
