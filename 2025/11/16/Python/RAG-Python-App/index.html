RAG Python App

项目背景

项目代码参考了 Tech with Tim 的 Production-Grade RAG 教程，并在原版基础上做了一些本地化改造：

  • 把 OpenAI 的嵌入模型换成 SiliconFlow 上的 BAAI/bge-m3（国内可直连、免费额度充足）
  • 把 OpenAI 的 LLM 换成 DeepSeek 的 deepseek-chat
  • 配套调整了向量维度（1024）、prompt 模板等

改造后的代码已开源在 GitHub：ProductionRAGPythonApp，欢迎 PR！

但对我个人来说，跑起来只是起点，更重要的是借助这份代码完整搞懂 RAG 的核心思想——从 PDF 怎么变成向量、向量怎么存进数据库、检索出来的内容怎么拼成 LLM 的提示词，到最终怎么打包成可交互的 Web 应用。这篇博客就是我整理出来的学习笔记。

项目的环境配置与启动方法请直接参考仓库 README，本篇主要聚焦为什么这样写和每个库在干什么。

(2) uv 是什么？为什么要用它？

uv 是什么？

uv 是 Rust 写的下一代 Python 包管理器，由 Ruff 同一团队出品。它可以理解为 pip + virtualenv + pyenv + poetry 的"全家桶"替代品，目标是把上面这一堆工具的所有功能用一个二进制实现，并且快上一个数量级（10~100 倍）。

简单来说：装它一个，你就不用再纠结"该用 pip 还是 poetry 还是 conda"了。

来看下主流工具的对比：

工具 速度 依赖解析 锁文件 虚拟环境 Python 版本管理 项目管理
pip 慢 弱（无完整解析） ❌ ❌ ❌ ❌
pip-tools 慢 强 ✅ ❌ ❌ ❌
poetry 中 强 ✅ ✅ ❌ ✅
conda 慢 中 部分 ✅ ✅ 部分
uv 极快 强 ✅ ✅ ✅ ✅

uv 的核心优势：

  1. 快得离谱：得益于 Rust + 全局缓存，第一次安装本项目的依赖大约 10 秒，之后几乎瞬时
  2. 自带 Python 版本管理：不再需要 pyenv install 3.12，uv 会按需自动下载
  3. 一份 pyproject.toml + uv.lock 走天下：跨机器、跨平台复现一致的环境

(3) 用 uv 初始化项目

执行后会在当前目录生成以下文件：

逐个看一下它们的职责：

  • pyproject.toml：项目的"身份证 + 货物清单"。声明项目名称、版本、Python 版本要求、第三方依赖。uv add、uv sync、甚至 pip install . 都会读这个文件
  • .python-version：仅一行内容（如 3.13）。uv 进入目录时会自动切换到这个版本，相当于隐式的 pyenv local
  • .gitignore：自动忽略 .venv/、__pycache__/、.env 等，省得手写
  • uv.lock（首次 uv sync 后生成）：精确锁住每个依赖（包括间接依赖）的具体版本和文件 hash，是跨机器复现的"定海神针"

pyproject.toml vs uv.lock 的区别（容易混淆）

  • pyproject.toml：你写的"愿望清单"，比如 fastapi>=0.116.1（“我要 0.116.1 或更新的”）
  • uv.lock：uv 实际安装的"购物小票"，比如 fastapi==0.116.3（“我这台机器上最终装的是 0.116.3”）

pyproject.toml 是给人看的、可宽可窄；uv.lock 是给机器看的、必须精确。两个文件都应该提交进 git——前者告诉协作者"项目需要什么"，后者保证"我们装的东西完全一样"。

RAG 基本原理

在学习代码之前，我们先建立对 RAG 的整体认知。RAG 全称 Retrieval-Augmented Generation，即"检索增强生成"，是构建个人/企业知识库问答系统的核心技术。

为什么需要 RAG？

当前主流大模型（ChatGPT、Gemini、DeepSeek、Claude 等）都是通用型的——它们在海量公开语料上预训练，但对你的私有数据一无所知。比如：

  • “学校南门每晚几点关门？”
  • “矿大宿舍的报修电话是多少？”
  • “公司今年的 Q3 销售目标完成率？”

通用模型要么胡编（幻觉），要么直接说"不知道"。

▶
RAG 相较于"直接把文件传给大模型"的优势？

ChatGPT、Kimi、DeepSeek 现在都支持上传文件直接问答，看起来 RAG 似乎"多余"。但实际上，RAG 在以下场景更有优势：

  1. 身份的转变：从"使用者"变为"创造者"。你可以把 RAG 嵌入自己的产品，做成面向特定人群的 AI 助手
  2. 解决幻觉问题：通过精准控制检索结果 + 要求引用来源，可以构建可信的 AI 应用，这是企业级场景的刚需
  3. 应对海量文档：当知识库包含成千上万份文档时（远超模型上下文窗口），文件上传功能根本无法工作，必须靠 RAG 的"先检索再生成"模式
  4. 数据隐私：敏感数据可以保留在本地向量库，每次只把相关 chunk 喂给模型，而不是整份文档上传
  5. 成本控制：RAG 每次只发送 Top-K 个 chunk（几千 token），而上传整份 PDF 可能是几十万 token——长期使用成本天差地别
  6. 技术集成的核心：RAG 是把向量数据库、嵌入模型、LLM 这些 AI 核心组件串联起来的"胶水"。学懂 RAG，等于打通了现代 AI 应用开发的核心技术栈。

(i) 索引阶段（Ingestion）

在用户提问之前，需要先把文档处理成"方便快速查找"的形式：

  1. 加载数据：读取 PDF、Word、TXT、HTML、数据库记录等格式的文档
  2. 分块（Chunking）：把长文档切成更小、语义完整的"文本块"。切太大检索精度差，切太小上下文丢失
  3. 向量化（Embedding）：用嵌入模型把每个文本块转换成一串数字（向量）。语义相近的文本，向量在数学空间中距离也更近——这是 RAG 的数学基础
  4. 入库（Upsert）：把向量 + 原文 + 元数据（文件名等）一起写入向量数据库

(ii) 检索阶段（Retrieval）

用户提问时，系统需要从数据库中找出最相关的 K 个 chunk：

  1. 查询向量化：用与索引阶段相同的嵌入模型，把用户问题也变成向量（注意：必须用同一个模型，否则两个向量不在同一个空间）
  2. 相似度搜索：在向量数据库中，计算查询向量与所有 chunk 向量的距离（通常用余弦相似度），找出最近的几个
  3. 返回 Top-K：取出最相关的 K 个 chunk（K 一般取 3~5），作为回答的依据

(iii) 生成阶段（Generation）

把检索到的 chunk 拼进 prompt，让 LLM 基于这些"开卷资料"生成回答：

  1. 拼接提示词：把检索到的 chunks 按固定模板拼成 context，加上 system 指令（“只基于 context 回答”）和用户问题
  2. 调用 LLM：把整个 prompt 发给大模型，让它"开卷答题"
  3. 返回答案：LLM 的回答返回给用户，同时附上引用的源文件（sources）

理解了这个三阶段框架，下面看代码就会清晰很多——每个 .py 文件都对应其中一部分。

代码详解

custom_types.py：项目数据类型

先看最小的文件，它定义了贯穿整个项目的几个 Pydantic 数据模型：

为什么用 Pydantic 而不是普通 dataclass 或 dict？

Pydantic 是 Python 生态最流行的数据验证库，相对于原生 dataclass 有几个优势：

  • 运行时类型校验：传错类型（比如把字符串塞进 list[str]）会立刻报错，而不是等到运行一半才崩
  • 自动序列化：.model_dump() 转 dict、.model_dump_json() 转 JSON，对接 API 极方便
  • Inngest 集成：本项目里 PydanticSerializer() 让 Inngest 步骤之间可以传递这些对象

main.py：工作流编排中心

main.py 是整个 RAG 应用的"指挥中心"——它把 FastAPI（Web 框架）与 Inngest（无服务器工作流引擎）结合，把 PDF 入库与问答检索这两个耗时任务封装为可观测、可重试、可限流的异步函数。

为什么需要 Inngest？

PDF 解析、分块、向量化、写库是一个可能耗时几十秒甚至几分钟的长任务。如果直接放在 HTTP 请求里同步处理：

  • 前端 HTTP 客户端会先超时
  • 一旦中途失败（比如网络抖动），整个流程要重来
  • 多用户同时上传时无法排队

Inngest 通过"事件触发 + 步骤函数"的模型解决了这些问题：

  • 事件驱动：业务代码只 send 一个事件，Inngest 负责调度
  • 步骤化（step）：每个步骤独立持久化，失败时只重试失败的那一步
  • 可观测：在 localhost:8288/runs 控制台可以看到每一步的状态和输出
  • 限流：throttle + rate_limit 防止恶意刷接口

两个限流策略协同工作：

关于 ID 生成的细节

这里用了 uuid5（基于命名空间 + 字符串的确定性 UUID），而不是 uuid4（随机）：

  • uuid4()：每次调用都生成新的随机 ID，重复入库会产生重复向量
  • uuid5(NAMESPACE, "report.pdf:0")：相同输入永远得到相同 ID，触发 Qdrant 的幂等 upsert（同 ID 覆盖）

这个细节在生产环境非常重要——没有它，用户重传同一份文件会让数据库膨胀好几倍。

data_loader.py：把 PDF 变成向量

data_loader.py 负责 RAG 流水线中最"脏"的部分——把 PDF 变成模型能消化的向量。它由两个核心函数组成：load_and_chunk_pdf（加载分块）和 embed_texts（向量化）。

(1) OpenAI 客户端的"伪 OpenAI"用法

注意这里用的是官方 openai 库，但传入的是 SiliconFlow 的 base_url 和 key——这是因为 SiliconFlow 兼容了 OpenAI 的接口规范，所以代码可以零改动迁移。同理，DeepSeek、Moonshot、智谱、零一万物等国内主流服务也都兼容此协议。

这意味着：学会一套 OpenAI SDK 用法，等于学会了所有国内主流大模型 API。

(2) SentenceSplitter 的两个关键参数

  • chunk_size=1000：每个文本块约 1000 个 token（≈ 750 个英文单词 / ≈ 1500 个汉字）。这是经过实践验证的"甜点值"——太短会让语义碎片化，太长会引入无关噪声、检索精度下降
  • chunk_overlap=200：相邻块之间重叠 200 token，避免关键信息被切到块边界而丢失上下文
▶
为什么不直接按字符切分？

按字符（比如每 1000 字一刀）会有两个致命问题：

  1. 语义断裂：一句话可能从中间被截断，检索出来的 chunk 上下文不完整，LLM 看不懂
  2. 指代丢失：例如 “它” “该方案” 这类代词的指代对象可能在另一个 chunk 里，单独看一个 chunk 等于没看

SentenceSplitter 的策略是：

  • 优先按句子边界切分（找 .、。、!、? 等终结符）
  • 再在 token 数上聚合到接近 chunk_size
  • 最后通过 chunk_overlap 把每块的尾部"借"给下一块的头部

这样最大程度保留了语义完整性。

(3) EMBED_DIM = 1024 的含义

这个值必须和你选用的 embedding 模型严格匹配。本项目使用 BAAI/bge-m3，输出维度就是 1024。

新手最容易踩的坑：换 embedding 模型时只改了 EMBED_MODEL 没改 EMBED_DIM。

  • 如果换成 OpenAI 的 text-embedding-3-small（1536 维），却忘了改这里的 1024
  • Qdrant 在创建 collection 时虽然不会立即报错（它不知道实际向量多长）
  • 但第一次写入向量时会因为维度不匹配直接报错

更麻烦的是：一旦 collection 创建成功，维度就锁死了。要换维度必须删掉 collection 重建。

常用模型的维度速查：

模型维度
BAAI/bge-m31024
BAAI/bge-large-zh-v1.51024
OpenAI text-embedding-3-small1536
OpenAI text-embedding-3-large3072
Cohere embed-multilingual-v31024

(4) embed_texts 的批量调用

这里一次性传入整个 list，比循环调用 embed_texts(chunk) 快得多——前者只走一次网络往返，后者要 N 次。对于 100 页的 PDF（约 200 个 chunk），这个差异可能是 30 秒 vs 3 分钟。

不过要注意：API 对单次请求的 token 数有上限（SiliconFlow 一般是 500K tokens/请求），超大文档需要自己分批。

vector_db.py：与向量数据库打交道

vector_db.py 封装了与 Qdrant 向量数据库的交互，是一个极简的 DAO（Data Access Object）层，只暴露两个方法：upsert（写入）和 search（检索）。

(1) Qdrant 的数据组织：类比关系数据库

Qdrant 的数据组织层级是 Collection → Point → Vector + Payload，可以类比关系数据库：

Qdrant 概念 关系数据库类比 本项目里是什么
Collection 表（Table） docs（所有 PDF 的 chunk 都存这一张"表"）
Point 行（Row） 一个文本块
Vector 一个特殊的高维列 1024 维浮点数
Payload 其他字段 {"source": "report.pdf", "text": "..."}
ID 主键 uuid5 生成的确定性 UUID

__init__ 中的 collection_exists 检查 + create_collection 是典型的懒加载初始化——首次写入时自动建表，避免手动 DDL 操作。

(2) 距离度量：为什么选 Distance.COSINE

Qdrant 支持三种距离度量：

度量 公式 含义 适用场景
COSINE 1 - (a·b) / (|a|·|b|) 余弦相似度（忽略向量长度） 文本语义检索（首选）
DOT -a·b 负点积（受向量长度影响） 已归一化的向量
EUCLID ‖a-b‖ 欧氏距离（几何距离） 图像特征、声纹

文本向量化后，我们关心的是"方向是否一致"（语义相似），而不是"模长是否接近"（向量长度往往受文本长度影响，无关语义）。所以余弦距离是文本检索的事实标准。

▶
三种距离的本质区别（数学直觉）

假设有两个向量：

  • A = [1, 0]（“猫”）
  • B = [2, 0]（“猫猫猫”，重复三次但语义没变）
  • C = [0, 1]（“狗”）

直觉上：A 和 B 应该"非常相似"（都讲猫），A 和 C 应该"不相似"（猫 vs 狗）。

  • 余弦距离：A vs B = 0（完全重合），A vs C = 1（正交）✅ 符合直觉
  • 欧氏距离：A vs B = 1，A vs C = √2 ≈ 1.41 ❌ B 因为"长度更长"被推远了
  • 点积：A·B = 2，A·C = 0 ❌ 同样受长度干扰

文本场景下，"猫"和"猫猫猫"应该被认为语义相同——所以余弦距离胜出。

(3) search 中的去重技巧

Top-K 检索返回的 K 个 chunk 可能全部来自同一个文件（比如只上传了一份 PDF 时）。用 set() 对 source 去重，最终只返回涉及的文件列表——这就是为什么前端能展示"答案引用自哪些 PDF"。

streamlit_app.py：用户交互界面

Streamlit 是 Python 的"Web UI 速成框架"，几十行代码就能搭出可交互的 Web 界面，完全不用写 HTML/CSS/JS。本项目用它实现了 PDF 上传和问答两个核心交互。

整个文件分为四个模块：Inngest 客户端、PDF 上传、提交问题、轮询结果。

(1) 初始化与 Inngest 客户端

Streamlit 的执行模型（重要）

Streamlit 的脚本有个反直觉的特性：每次用户交互（点按钮、输入文字、上传文件）都会从头到尾重跑一遍整个脚本。

这就是为什么 @st.cache_resource 这么重要——它让 Inngest 客户端、数据库连接等"昂贵对象"只创建一次，后续重跑直接复用缓存。不加的话，每点一次按钮就重建一次连接，很快就会资源耗尽。

(2) PDF 上传与事件触发

这里有一个关键设计：Streamlit 把 PDF 保存到本地 uploads/ 目录，然后只把"文件路径"作为事件 data 发给 Inngest，而不是把整个 PDF 字节流塞进事件。这样做的好处：

  • 事件 payload 不会过大（PDF 可能几十 MB，事件系统不适合扛这种负载）
  • 后端函数可以按需重新读取文件（重试时也不用重新传）
  • 多个 worker 可以共享访问同一份文件

(5) Streamlit 表单 UI

top_k 的取值建议

top_k 决定从向量数据库检索多少个 chunk 喂给 LLM：

  • top_k=3~5：适合事实型问答（“X 的定义是什么？”），context 干扰少、token 省钱
  • top_k=10+：适合对比型 / 综述型问答（“A、B、C 三种方案的差异？”），需要更多上下文综合

但要注意：top_k 越大，prompt 越长，信息淹没和token 成本都会上升，并不总是越准。新手建议从 5 开始试。

完整调用链回顾

至此，整个 RAG 应用的数据流就完全串起来了。入库与问答是两条独立的链路：

入库链路（PDF → 向量数据库）

  1. 用户在 Streamlit 上传一份 PDF
  2. save_uploaded_pdf() 把文件保存到本地 uploads/ 目录（实际文件落地）
  3. send_rag_ingest_event() 发送 rag/ingest_pdf 事件给 Inngest（事件只带文件路径，不带字节）
  4. Inngest 调度 main.rag_ingest_pdf 函数，分两步执行：
    • Step 1 load-and-chunk：data_loader.load_and_chunk_pdf() 用 PDFReader 解析 + SentenceSplitter 切块
    • Step 2 embed-and-upsert：data_loader.embed_texts() 把每个 chunk 转成 1024 维向量，QdrantStorage().upsert() 写入 Qdrant

问答链路（问题 → 答案）

  1. 用户在 Streamlit 输入问题 + top_k
  2. send_rag_query_event() 发送 rag/query_pdf_ai 事件给 Inngest，返回 event_id
  3. Inngest 调度 main.rag_query_pdf_ai 函数，分两步执行：
    • Step 1 embed-and-search：embed_texts([问题]) 把问题转成查询向量，QdrantStorage.search() 取回 Top-K 个 chunks
    • Step 2 llm-answer：拼接 System + Context + Question，通过 OpenAI 兼容 adapter 调用 DeepSeek，返回 answer + sources
  4. Streamlit 轮询 /v1/events/{id}/runs，等 status == Completed 后取出 output，展示 answer + sources

五个文件职责一览

文件 职责 关键技术
main.py 工作流编排 FastAPI + Inngest + Pydantic
data_loader.py PDF → 向量 llama-index + OpenAI SDK
vector_db.py 向量存取 Qdrant + 余弦相似度
streamlit_app.py 用户交互 Streamlit + 异步轮询
custom_types.py 类型定义 Pydantic BaseModel

写到这里，整个项目从 PDF 上传到问答输出的全流程就梳理完了。在这之后可以尝试替换 embedding 模型、加入 rerank（重排序）、改造为多模态 RAG、或者把 Inngest 换成 Celery——这些都建立在对当前架构的理解之上。

如果遇到看不懂的代码，直接去 Inngest 控制台（localhost:8288/runs）看实际运行日志，里面的 step 输入输出都很清晰，比反复读代码更直接。

进阶：如何评估与提升 RAG 效果

项目跑起来只是起点。一个常见的困惑是——怎么知道我的 RAG 系统答得好不好？ 改了一个参数（比如 chunk_size、top_k、换了个 embedding 模型），到底是变好了还是变差了？没有量化指标就只能靠感觉调参，而感觉往往是错的。

这一节聊聊 RAG 的评估指标体系，以及最关键的指标——召回率（Recall）——怎么提升。

(1) RAG 的核心评估指标：RAG 三元组

业界主流框架是 TruLens 提出的 RAG Triad（RAG 三元组），从三个维度评估：

指标 评估什么 关注环节
Context Recall（上下文召回率） 该检索到的相关内容有没有漏掉 检索阶段
Context Precision（上下文精确率） 检索出来的内容有多少是真正相关的 检索阶段
Faithfulness（忠实度） 答案是不是真的基于检索到的内容（防幻觉） 生成阶段
Answer Relevancy（答案相关性） 答案有没有真正回答用户的问题 生成阶段

四个指标对应 RAG 的两大环节（检索 + 生成），覆盖了"找得全、找得准、答得真、答得对"四个维度。

(2) 召回率（Recall）：最致命的指标

直观理解

召回率 = 找回来的相关内容 / 应该被找回来的全部相关内容

举个例子：

为什么 Recall 比 Precision 更关键

RAG 场景下，召回率往往比精确率更要命：

  • Recall 低 → LLM 根本看不到关键信息 → 答错或不知道（用户直接感知）
  • Precision 低 → 检索结果混入无关内容 → LLM 大多能自行忽略 → 答案还是对的

一句话总结：Recall 决定下限，Precision 影响上限。所以优化 RAG 通常先攻 Recall。

▶
Recall 和 Precision 的数学定义

$$
\text{Recall} = \frac{|{\text{相关 chunk}} \cap {\text{检索 chunk}}|}{|{\text{相关 chunk}}|}
$$

$$
\text{Precision} = \frac{|{\text{相关 chunk}} \cap {\text{检索 chunk}}|}{|{\text{检索 chunk}}|}
$$

分子相同（都是"找对的部分"），分母不同：

  • Recall 的分母是"应该找到的总量"——衡量覆盖率
  • Precision 的分母是"实际返回的总量"——衡量准确率

正确用法是看相对变化：基线版本跑一次，改完代码再跑一次，对比分数升降。

(5) 提升召回率的 9 种方法

按性价比从高到低排序：

① 重排序（Rerank）⭐⭐⭐⭐⭐ 最立竿见影

两阶段检索：阶段 1 用向量检索召回 Top-50（高召回、低精度），阶段 2 用 Cross-Encoder 精排取 Top-5（高精度），最后拼 prompt 给 LLM。

为什么有效：

  • 向量检索用的是 Bi-Encoder（问题和文档分别编码再算相似度），快但精度有限
  • Cross-Encoder 把问题和文档拼在一起送模型，精度高但慢
  • 两阶段组合 = 又快又准

主流 Rerank 模型：

模型 类型 备注
BAAI/bge-reranker-v2-m3 开源 多语言、推荐
Cohere Rerank 商业 API 效果稳，按调用收费
Jina Reranker 开源 也不错

② 混合检索（BM25 + 向量）⭐⭐⭐⭐⭐

用户问题同时走两路检索——向量检索抓语义相似、BM25 抓关键词精确匹配，然后用 RRF（Reciprocal Rank Fusion） 算法融合两路结果。

两者互补：

  • 向量检索：擅长语义相似（“小猫” → 能匹配"猫咪"）
  • BM25：擅长关键词精确匹配（产品代号 SKU-12345、人名、专有名词）

融合算法常用 RRF（Reciprocal Rank Fusion）。生产环境通常能提升 Recall 10~30%。
