静态页面爬取

浏览器访问网页的本质，是向服务器发送一个 HTTP 请求，服务器收到后返回 HTTP 响应（也就是我们在浏览器里看到的页面内容）。Python 的 requests 库让我们能用代码完成同样的过程。

服务器返回响应时会附带一个状态码，用来表示请求的处理结果：

状态码 含义
2xx 请求成功
4xx 客户端错误
5xx 服务器错误

所以我们可以根据状态码的范围判断请求是否成功：

上面这种范围判断其实有点繁琐，更简单的做法是直接用 response.ok：当状态码在 200~399 之间时它返回 True，否则返回 False。

前面这几次请求用的都是默认请求头，但 requests 也允许我们自定义请求头。这样做最大的好处是可以把爬虫程序伪装成正常浏览器，避免被服务器识别为机器人而拒绝访问——有些服务器会通过请求头里的 User-Agent 字段判断请求方是不是真实浏览器，只服务于「真人用户」。

如何获取 User-Agent：在浏览器中打开任意网页 → 右键「检查」（或直接按 F12）→ 切换到「网络 / Network」面板 → 任选一条请求，把请求头中 User-Agent: 后面的那串字符串复制出来即可。

requests 拿到的只是 HTML 字符串，要从中提取信息还得靠 BeautifulSoup。它本质上是一个 HTML 解析器，能把看上去杂乱的 HTML 字符串解析成一棵树形结构，让我们可以按标签名、属性、CSS 选择器等方式精确地定位元素。

soup.p 只能拿到第一个匹配的标签，而 find_all() 会返回所有匹配的标签。要从一堆 HTML 里准确提取目标信息，关键在于先观察网页源代码——分析目标信息的标签结构特点（标签类型、class 名、嵌套层级等），再据此选择合适的提取方式。

爬取动态渲染页面

前面我们用 requests + BeautifulSoup 顺利爬取了豆瓣 Top250 和图书网站，但你会发现，这套方法并不是万能的。试着用同样的代码去爬取 B 站首页的视频列表、微博热搜、小红书笔记，或者任何一个由 React/Vue 构建的单页应用（SPA），你会拿到一份几乎为空的 HTML 骨架——你想要的内容根本不在源代码里。

根本原因：服务端渲染 vs 客户端渲染

渲染方式数据在哪requests 能抓吗？
SSR（服务端渲染）数据直接写在返回的 HTML 里✅ 能
CSR（客户端渲染）HTML 只是空壳，数据由浏览器执行 JS 后通过 AJAX 二次请求拿到❌ 不能

豆瓣 Top250 是 SSR，所以一发请求就拿到完整页面；而 B 站、微博是 CSR，requests 拿到的只是 JS 还未执行的 HTML 外壳，自然什么都提取不到。

判断一个页面是不是 CSR 最简单的方法：右键「查看网页源代码」→ Ctrl+F 搜索页面上的一段具体文字，搜不到就是 CSR。下面我们以官方的 CSR 演示站 quotes.toscrape.com/js/ 为例，演示三种解决方案。

浏览器里明明能看到几十条名言，但代码却抓到 0 条——这就是典型的 CSR 页面。下面看看怎么解决。

方案一：抓包找接口（首选，效率最高）

CSR 页面的数据本质上是一次 AJAX 请求拿到的 JSON。既然数据本身就是结构化的 JSON，我们直接找到这个接口调用即可，没必要再解析 HTML。

操作方法：在目标页面按 F12 → 切换到 Network（网络） 面板 → 筛选 Fetch/XHR → 刷新页面 → 逐个点开请求查看 Response，找到返回目标数据的那条。

关键点在 response.json()：返回的本身就是结构化字典/列表，可以直接通过键名索引取值，比解析 HTML 方便得多。

实际项目里的坑：真实的接口往往会校验 Referer、Cookie，甚至要求带 sign、_signature 这类由前端 JS 加密生成的签名参数。遇到加密签名时，要么逆向 JS 算法（成本高），要么直接放弃走接口方案，改用下面的浏览器自动化。

方案二：Playwright（新项目首选的浏览器自动化）

接口走不通时，就用浏览器自动化——让程序启动一个真实浏览器，等 JS 执行完再拿 HTML。Playwright 是微软开源的新一代工具，相比 Selenium，API 更现代、自带浏览器内核、无需手动装驱动。

方案三：Selenium（经典方案，老项目兼容性好）

Selenium 是浏览器自动化的元老，教程多、生态成熟，但需要单独下载浏览器驱动（chromedriver）且版本必须匹配，体验不如 Playwright 顺滑。维护老项目或要用 Selenium Grid 集群时才首选它。

三种方案怎么选

维度 找接口（requests） Playwright Selenium
速度 ⚡ 极快（毫秒级） 秒级 秒级
资源占用 极低 较高（启动浏览器） 较高（启动浏览器）
开发难度 看接口是否加密 简单 简单
抗风控能力 弱 强（真实浏览器） 强（真实浏览器）
适用场景 数据量大的批量抓取 新项目首选 老项目维护

选型流程：先用 requests 试一下 → 抓不到就看 F12 有没有现成可调的 API 接口 → 接口被加密就用 Playwright。除非维护老代码，否则不必再首选 Selenium。

开源框架：MediaCrawler

前面讲的都是从零开始写爬虫。但如果你的目标是小红书、抖音、B 站、微博、知乎、贴吧、快手这些主流社交平台，完全不需要自己造轮子——这些平台的接口签名算法极其复杂（JS 混淆 + 动态密钥 + 设备指纹），自己逆向可能要花几周。这时可以直接用社区已经做好的开源框架 MediaCrawler（截至 2026 年 7 月，43K+ Star）。

MediaCrawler 的核心思路：用 Playwright 启动一个真实浏览器 → 手动扫码/短信登录 → 保留登录态后的浏览器上下文，直接在里面执行 JS 表达式拿到签名参数 → 再用这些参数去调平台的真实接口。

这种「用登录态绕过 JS 逆向」的设计是它最大的亮点——不需要破解任何加密算法，门槛极低，效果却和真人在浏览器里操作一模一样。

支持的平台与功能：

平台 关键词搜索 指定帖子 ID 二级评论 创作者主页 登录态缓存 IP 代理池
小红书 / 抖音 / 快手 ✅ ✅ ✅ ✅ ✅ ✅
B 站 / 微博 / 知乎 / 贴吧 ✅ ✅ ✅ ✅ ✅ ✅

数据可保存为 CSV / JSON / JSONL / Excel / SQLite / MySQL 任一格式。

命令参数含义：

  • --platform xhs：指定平台，xhs（小红书）/ dy（抖音）/ ks（快手）/ bilibili / wb（微博）/ zh（知乎）/ tieba
  • --lt qrcode：登录方式（qrcode 扫码 / phone 手机号 / cookie 直接粘贴 Cookie）
  • --type search：爬取类型（search 关键词搜索 / detail 指定帖子 ID / creator 指定创作者主页）

具体的关键词、帖子 ID、是否爬评论等细节，都在 config/base_config.py 里配置，注释是中文的，按需修改即可。

几点重要提醒：

  • MediaCrawler 默认使用 CDP 模式——连接你电脑上已经打开并登录的 Chrome 浏览器，复用现成的 Cookie 和登录态，进一步降低风控风险。使用前需要在 Chrome 地址栏访问 chrome://inspect/#remote-debugging 勾选「Allow remote debugging」
  • 项目作者明确声明仅供学习研究，禁止商业用途，使用时务必遵守目标平台的 robots 协议和当地法律法规
  • 这类项目迭代很快，平台风控也在持续升级，遇到接口失效属正常现象，关注仓库的 Issue 和 Release 跟进修复

爬虫礼仪与反爬

无论用哪种方案，请务必遵守基本的爬虫礼仪：

  • 遵守 robots.txt：访问 网站域名/robots.txt 查看对方允许/禁止抓取哪些路径
  • 控制请求频率：加上 time.sleep()，避免对目标服务器造成压力（一般 1~3 秒一次较为安全）
  • 不抓取敏感数据：个人隐私、登录态下的数据、付费内容等不要碰
  • 不商用/不滥用：抓到的数据仅供学习研究，切勿用于商业用途或大量分发
