Ollama API For Python

本文将会记录我第一次本地部署大模型并基于它进行 API 接口开发的全流程！

之所以想做这个项目，是因为之前调用 OpenAI、DeepSeek 等云端 API 时，总是会受到网络、API Key 额度、隐私数据等限制。而本地部署大模型恰好解决了这些问题——模型完全跑在自己的机器上，数据不会外泄，调用次数也没有限制。这对于学习、原型开发以及处理一些敏感数据的场景来说非常友好。

本地部署 vs 云端 API 的取舍

维度本地部署（Ollama）云端 API（OpenAI / DeepSeek）
隐私性✅ 数据不出本地❌ 数据需上传
成本一次性硬件投入按 token 计费
模型质量受限于本地显存顶级闭源模型
部署难度需配置环境一个 API Key 即可
响应速度取决于本地硬件通常更快更稳定

简言之：学习 / 隐私敏感场景 → 本地部署；生产 / 商用场景 → 云端 API。

本项目最终实现了一个基于 FastAPI 的轻量级 API 服务，具备：

  • ✅ API Key 鉴权：只有持有合法密钥的客户端才能调用
  • ✅ 额度管理：每个 Key 拥有初始调用次数限制，防止滥用
  • ✅ 本地推理：所有请求由本地 Ollama 模型处理，零外部依赖

SYSTEM 提示词的写作技巧

上面这段 SYSTEM 看起来很长，但其实遵循了一个非常实用的模板——「身份 + 专长 + 风格 + 适用场景」四段式：

段落作用关键写法
身份（Identity）锚定模型的人设与立场用「专家」而非「学生」 —— 模型会模仿人设的笃定程度，专家身份能换来更自信、更深入的回答
专长（Expertise）圈定知识范围，避免乱答列出关键技术栈、框架、相邻领域，相当于给模型划「能力边界」
沟通风格（Style）控制语气、格式、详略例如「先给代码再讲原理」「不确定时承认不知道」
适用场景（Scope）让回答更贴近使用者真实需求写明典型任务类型，模型会自动带入相关例子

写作时几个小经验：

  • 用「专家 / expert」给人设打标签：让回答更笃定、信息密度更高
  • 用具体名词代替形容词：「熟悉 Python」不如「主力语言 Python，熟悉 PyTorch、FastAPI」
  • 明确禁止行为：写上「Never fabricate」「不知道就说不知道」，能显著降低幻觉（hallucination）
  • 结构化排版：用 Markdown 标题 / 列表分隔段落，开源模型对小段落的「注意力」更集中
  • 写英文效果通常比中文好：Mistral、Llama 等模型预训练语料以英文为主，中文 prompt 容易触发翻译腔或简短回答

  • FROM <模型名>：指定基础模型（预训练模型或微调后的模型）（.gguf格式）

    • FROM llama2-7b（基于 Llama 2 的 70 亿参数模型）
    • FROM ./my_finetuned_model.gguf（本地微调后的模型文件）

.gguf是一种开源的大语言模型的文件格式

  • PARAMETER <参数名> <参数值>：指定模型参数
参数名作用常见取值范围 / 示例
temperature控制输出随机性（值越高越随机，越低越确定）0~2（例如：0.3（严谨）、1.5（发散））
top_k生成时仅从概率最高的k个词中选择（限制候选词范围）1~100（例如：50、10（更集中））
top_p（核采样）从累计概率超过p的词中随机选择（动态调整候选词数量）0~1（例如：0.9（常用）、0.5（更严格））
max_tokens限制生成的最大 token 数（避免输出过长）整数（例如：512、1024）
stop定义终止符（遇到该字符时停止生成）字符串（例如：stop: “###”、stop: “\n”）
repeat_penalty惩罚重复内容（值越高，越避免重复）1~2（例如：1.2（轻微惩罚）、1.8（严格））
presence_penalty惩罚已出现过的主题（鼓励新内容）-2~2（例如：0.5、-0.5（允许重复））
frequency_penalty惩罚高频出现的词（减少冗余词汇）-2~2（例如：0.3）

本项目的 Modelfile 同时设置了 temperature 0.7 + top_p 0.9 + repeat_penalty 1.1：中等创造性 + 略高多样性的组合，适合技术问答类场景——既能给出稳定的代码和解释，又不会每次都输出一字不差的样板答案。

  • SYSTEM "<提示词>"：定义模型的角色、行为规则或背景信息（引导模型生成符合设定的回复）。

根据自己需求修改好Modelfile文件后，就可以创建自定义模型了：

ollama create <模型名> -f <配置文件名>：根据模型名创建。创建成功后，用 ollama run cumt-cs-bot 即可与自定义人设的模型对话。

Modelfile vs OpenAI System Prompt

如果你用过 OpenAI 的 API，会发现两者都能设定模型的「人设」。区别在于：

  • Modelfile：在模型层面固化，每次调用都生效，适合稳定的角色设定（如本项目把模型固定为「Multi-Agent 系统专家」）
  • System Prompt：在每次请求的 messages 里传入，灵活但容易遗漏

实际项目中，可以把稳定的身份/语气交给 Modelfile，把具体任务指令放在请求的 system 消息里，二者配合使用。

About requirements

requirements.txt 是一个包含 Python 包依赖关系的文件，避免因依赖版本不兼容而出现 “It works on my machine” 的问题。

什么时候使用？

  • 项目协作：其他开发者拿到项目后，通过该文件可快速安装所需依赖，无需手动逐个查找库名和版本。
  • 部署项目：在服务器、容器（如 Docker）或云平台上部署时，通过该文件一键安装依赖，保证环境一致性。

为什么要有 .env 文件？

1. 保护敏感信息
项目中常涉及数据库密码、API 密钥、Token、密钥等敏感数据。如果直接写在代码里（比如 API_KEY = "abc123"），一旦代码上传到 GitHub 等公开仓库，这些信息会被泄露，导致安全风险。用 .env 存储这些信息，再通过 .gitignore 忽略该文件，可避免敏感信息泄露。
2. 区分环境配置
一个项目通常有开发环境（本地开发）、测试环境（测试服务器）、生产环境（线上服务器），不同环境的配置可能不同（比如数据库地址、API 域名）。用 .env 可以为不同环境创建不同的配置文件，切换环境时只需替换配置文件，无需修改代码。
3. 简化配置管理
当配置需要修改时，直接修改 .env 文件即可，无需在代码中逐个查找硬编码的配置，降低维护成本。

如何使用.env文件？

1. 为 键=值的形式（键值对）

2. 在代码中读取
需要借助工具库（如 Python 的 python-dotenv、Node.js 的 dotenv）加载 .env 中的配置到系统环境变量，再在代码中读取。

  • load_dotenv()：若不带参数，它会自动在当前工作目录中寻找名为 .env 的文件，并加载其中的环境变量。
  • 如果配置文件区分不同环境（如.env.dev），则需要通过 dotenv_path 参数指定文件路径：load_dotenv(dotenv_path=".env.dev")。

3. 忽略 .env 文件

  • verify_api_key：这是一个 FastAPI 的依赖项（dependency）函数，无需显式，框架就会帮你自动调用这个依赖函数。

  • x_api_key: str = Header(None):

    • x_api_key: str：这里是 Python 的类型注解，用来声明变量 x_api_key 的类型是 str
    • Header(None)：这是 FastAPI 的参数获取方式，指定 x_api_key 的值需要从请求头（Header） 中获取

  • raise HTTPException(status_code, detail)：这是 FastAPI 中用于主动抛出错误响应。

    • status_code=401：这是 HTTP 状态码，用于表示未授权（Unauthorized）错误。
    • detail="Invalid API Key, or no credits"：这是错误详情，当 API 密钥无效或无可用额度时，会返回这个错误信息。
  • @app.post("/generate")：这是 FastAPI 的路由装饰器
    • .post("/generate") ：当客户端以 POST 方法访问 /generate 路径时，会执行下面的 generate 函数。
    • Depends(verify_api_key)：表示在执行 generate 函数前，先执行 verify_api_key 函数（之前定义的密钥验证函数），并将其返回值传给 x_api_key，如果 verify_api_key 验证失败（抛出 401 错误），generate 函数不会执行，直接返回错误给客户端。
  • ollama.chat(model,messages)：用于与 AI 模型进行对话交互
    • model="mistral"：指定使用的 AI 模型是 “mistral”。
    • messages=[{"role": "user", "content": prompt}]：这是一个消息列表，包含一个用户消息。
      • "role": "user"：表示这是一个用户消息。
      • "content": prompt：用户消息的内容是 prompt 变量的值。

Ollama 的流式调用

回到本项目，ollama 库同样支持流式输出（streaming），只需在 chat 中加上 stream=True，返回值会变成一个可迭代的 chunk 流：

为什么要用流式？

  • 用户体验：边生成边显示，首字延迟从「等 10 秒看一坨」变成「立刻看到字一个一个蹦出来」，体感快得多
  • 可中途打断：在前端发现回答跑偏时可以随时取消请求，省 token
  • 长文本场景：写小说、代码、长报告时，非流式需要等几十秒才一次性返回，体验差

把流式接到 FastAPI 里时，路由函数需要声明为 async def 并使用 StreamingResponse 把 chunk 逐个 yield 给客户端。本项目为保持入门难度使用的是非流式，留作进阶练习。

总结

完成这个项目的过程中，我把自己当成「既是模型提供方、又是 API 开发者、还是调用方」三种角色走了一遍，对大模型应用的整条链路有了非常直观的认识。简单复盘下学到的东西：

  1. 本地大模型并不神秘——ollama run 一条命令就能跑起来，原理和 Docker 拉镜像类似
  2. API Key + 额度管理——这是几乎所有 LLM 服务（OpenAI / Anthropic / DeepSeek）的标配鉴权模式，本项目用 20 行代码就复刻了核心思路
  3. FastAPI 真的很省心——类型注解既当文档又当校验，/docs 自动生成，开发体验远好于 Flask
  4. .env + Depends 是 Python Web 项目里两个值得养成习惯的小工具——前者保护密钥，后者让鉴权逻辑干净复用

下一步可以做什么

  • 把额度字典换成 SQLite / Redis，让服务重启后额度不丢
  • 加上 /chat 接口支持多轮对话（保留 messages 上下文）
  • 接入 RAG（参见下一篇 RAG Python App），让模型回答自己的笔记 / 文档
  • 用 Docker 打包，部署到家里的小主机或 NAS 上，做成私人 LLM 服务
