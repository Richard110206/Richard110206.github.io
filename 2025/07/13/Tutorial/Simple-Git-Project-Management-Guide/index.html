Simple Git Project Management Guide

Git 是一个分布式版本控制系统(Vision Control Systems)，它允许多个人在同一项目上工作。通过 Git，我们可以记录项目的每一次更改，并且可以将代码推送到 GitHub，方便以后查看和分享（多人的协作开发）。以下是Git进行代码版本管理的基本操作：

Git Bundle：离线传输与无权限协作

Git 的分布式设计让每个仓库都是完整的，但仓库之间的同步通常依赖网络（push / fetch）。当网络不存在或权限不足时——隔离内网、无 push 权限的贡献者、U 盘摆渡、离线备份——git bundle 提供了官方的离线传输方案：把 refs 和打包后的对象装进一个文件，对方可以像对待远程仓库一样 clone / fetch 它。

前文已介绍 Git 的基本操作、快照模型与分支，本节补充这块离线场景下的知识。文中所有命令与输出均在 Git 2.52 上实际验证。

1、Git Bundle 是什么

Git Bundle 是一个单文件归档，同时携带"引用（refs）“和这些引用背后"打包的对象（packfile）”。它可以被 git clone、git fetch、git pull 直接当作远程仓库使用。

几个关键认识：

  1. .bundle 文件的本质：一段人类可读的文本头部 + 一个二进制 packfile。头部声明"我有哪些 ref、我假定你已有哪几个提交"，packfile 部分则是标准的 Git 对象包。它不是通用压缩格式，Git 之外的解压工具无法读取。

  2. 能保存什么：分支与标签指向的 commit / tree / blob / tag 对象，即完整的提交历史和每一次提交的精确内容。相应地，它不保存：工作区文件、暂存区、config（含 remote 定义）、hooks、.gitignore 规则本身、LFS 大文件内容、子模块仓库本体。

  3. 与 ZIP 的区别：ZIP 只是某一时刻工作目录的普通压缩，没有版本概念；bundle 是"版本库的切片"，保留 DAG 结构、提交者身份、时间戳、签名，接收方合并时与网络 fetch 完全等价。

  4. 与仓库的关系：可以把 bundle 理解为一个只读的、单文件的迷你远程仓库。它不能被直接 commit 或 push，但可以从中 fetch；接收方的 merge / cherry-pick / rebase 照常工作。

  5. 典型场景：

    • 无 push 权限的贡献者向维护者交付提交（第 4 小节的主角）；
    • 物理隔离网络之间的代码摆渡（U 盘 / 光盘）；
    • 离线环境初始化仓库：先传 bundle，再 git clone <bundle>；
    • 单文件备份：定期 --all 打包整个仓库的引用可达历史；
    • 慢速链路下的提速分发（Git ≥ 2.38 实验性的 git clone --bundle-uri=<url> 即基于此）。

2.2 对象如何保存：bundle 就是"固化的一次 fetch 会话"

回忆网络传输时发生的事情：服务端广播自己的 refs，客户端声明自己有哪些提交（have），服务端据此算出缺失对象集合，打成一个 packfile 发过来。

git bundle create 做的是同一件事，只是把结果冻结成文件：

  1. 参数被原样交给 git rev-list 语义解释（所以一切 rev-list 语法——分支名、A..B 范围、--all、--since——都可用）；
  2. 正向引用可达、负向引用不可达的对象集合被 git pack-objects 压缩成一个 packfile；
  3. 被排除在外的历史边界上的提交被写入头部，成为前置依赖。

因此：blob、tree、commit 在 bundle 中以 packfile 压缩格式原样存放，字节不变，SHA 不变。git bundle unbundle / git fetch <bundle> 时由 git index-pack 解包入库——与网络 fetch 的收包路径完全相同。

2.3 为什么 bundle 能"无损保留"提交历史

因为 Git 对象是内容寻址的：commit 对象的内容包含了父提交 SHA、作者、提交者、时间戳、提交信息，以及指向根 tree 的指针。bundle 传输的是对象本身而不是"补丁描述"，所以接收方拿到的提交 SHA 与发送方完全一致：

  • git log 看到的作者 / 提交者 / 时间戳 / GPG 签名全部一致；
  • git merge-base、git cherry-pick、git rebase 可以直接工作，就像刚执行过一次 git fetch；
  • 这也是 bundle 与 format-patch 的本质区别：后者传输的是"如何重建提交的说明"，接收方重新生成提交，SHA 会改变（详见第 6 小节对比）。

2.4 完整 bundle 与增量 bundle

区别只在一处：头部是否存在前置依赖行。

用前文的实验仓库示意（沿用《关联快照》中的 o <-- o 提交图记法）：

  • git bundle create full.bundle main：打包 main 可达的全部对象。无前置依赖（git bundle verify 会提示 The bundle records a complete history.），拿到任何机器都能直接 clone；
  • git bundle create incr.bundle origin/main..main：只打包 origin/main 不包含、而 main 新增的对象。origin/main 的 tip 成为前置依赖，接收方必须已拥有该提交。

一个直观的体积感受（本实验仓库）：2 个提交的增量 bundle 约 0.4 KB，包含全部引用的完整 bundle 约 1.2 KB——packfile 压缩 + 增量裁剪使 bundle 通常远小于 .git 目录。

2.5 前置依赖（Prerequisites）的含义

前置依赖行声明的是契约：“我假定你的仓库里已经有这些提交；否则我的 packfile 对你不完整”。git bundle verify 在接收方仓库中逐个检查这些 SHA 是否存在，缺失则拒绝并报错：

注意它检查的是对象存在性（按 SHA），与对方把这些提交放在哪个分支、哪个 ref 上无关。这解释了第 5 小节"增量 bundle 可移植性"问题的根源。

4.3 三个安全问题

如何确保不覆盖 B 已有的工作？
merge / cherry-pick / fetch 本身都是只增不改的操作，真正的风险只在 push。规程：改动只进入 alice-main 临时分支 → 在 main 上以 merge 方式合入（冲突当场解决，历史双方都保留）→ push 前用 --dry-run 与 git log origin/main..main 双重核对。绝不在协作仓库上使用 git push -f。

如何避免错误地推送分支？
永远使用显式 refspec（git push origin main），不依赖 push.default 的隐式行为；多分支仓库中先 git log origin/main..main 看清"将要推什么"。若确需覆盖远端（例如 B 本地做过 rebase），用 git push --force-with-lease origin main，它在远端被他人更新过时拒绝执行，是强制推送的安全形态。

5、进阶用法

1. 完整 bundle（备份 / 全新环境初始化）

无前置依赖的 bundle 可在任何机器 git clone，这是它适合做备份单元的原因。

2. 增量 bundle（多轮离线交付）

下一轮交付前，A 应先 git fetch origin 拿到 B 已合入的结果，新的增量范围才不会越来越臃肿（实测第二轮 bundle 仅含新提交，依赖指向 A 刚 fetch 到的 origin/main）。

3. 指定分支或 tag

4. 只传特定范围的提交

范围端点中被排除一侧的 tip 会自动成为前置依赖。

5. 用 bundle 更新已有仓库
就是 3.6 的 fetch / pull：git fetch new.bundle main:alice-main。也可以把 bundle 注册成固定 remote（文件路径可作 URL）：git remote add offline /path/x.bundle，之后 git fetch offline——换新 bundle 时覆盖同一路径文件即可。

6. 验证前置依赖
git bundle verify <file> 是唯一权威手段：依赖满足时列出 requires this ref 并输出 is okay；不满足时点名缺失的提交并以非零码退出。批量归档场景应在接收端脚本里以退出码做闸门。

7. 为什么增量 bundle 不能保证在任意仓库使用？
前置依赖按 SHA 匹配。以下接收方都会验证失败：浅克隆（--depth，历史被截断）、经历过 rebase / filter-branch / reclone 的仓库（SHA 已改写）、或干脆是另一个项目。这不是 bug 而是契约——依赖行的存在就是声明"只保证在拥有这些提交的仓库中可用"。补救：请发送方扩大范围（如直接 main 全量）或改发完整 bundle。

6、与 Patch / Archive / ZIP 的对比

维度 Git Bundle Git Patch（format-patch / am） Git Archive ZIP / tar
保存的内容 refs + packfile（对象库切片） 提交的差异文本（邮件格式） 某次提交的目录内容 任意文件的字节压缩
含提交历史 ✅ 完整 DAG ⚠️ 提交信息保留，但按"重放"重建 ❌ 仅单个快照 ❌ 无版本概念
保留提交身份 ✅ SHA、作者、提交者、签名逐位一致 ⚠️ 作者保留，提交者与 SHA 改变 ❌ ❌
离线传输 ✅ 单文件，U 盘 / 邮件 ✅ 纯文本，可直接贴邮件正文 ✅ ✅
可恢复仓库 ✅ clone / fetch 即得完整仓库 ⚠️ 逐个 am 重建，无分支 / ref 语义 ❌ 只能得到工作区 ❌
增量传输 ✅ 范围语法原生支持 ✅ 每提交一个补丁 ❌ ❌
典型场景 无权限 / 隔离网络交付、单文件备份 邮件列表工作流（如内核）、逐提交评审 发布源码快照 日常文件压缩

经验法则：要"仓库对仓库"的等价传输用 bundle；要"人对人"的逐提交评审用 patch；要给别人编译用 archive/zip。

7、边界与注意事项

  1. 未 commit 的修改：不包含。bundle 只打包 refs 可达的对象；工作区与暂存区的改动尚不是对象。交付前先 commit，或用 git stash / git diff 另行处理。
  2. .gitignore 忽略的文件：不包含。忽略规则使这些文件从未被跟踪、不存在于对象库中；.gitignore 文件本身若被跟踪则会随历史打包。
  3. Git LFS 对象：内容不包含。LFS 在仓库里只存指针文件（普通 blob，会进 bundle），真实大文件在 LFS 存储服务或 .git/lfs/objects 中。离线场景需发送方 git lfs fetch --all 后另行打包 .git/lfs/objects，接收方解包到对应位置。
  4. Submodule：父仓库中的 gitlink（子模块的 commit SHA 记录）会随 tree 对象打包，但子模块仓库的对象不包含在 bundle 里。离线接收方无法仅凭父仓库 bundle 还原子模块，需单独为每个子模块制 bundle，或联机执行 git submodule update --init。
  5. 远程仓库权限配置：不包含。remote 定义、凭据、分支保护、hooks、config 都留在各自仓库中；bundle 只是数据 + 引用。clone 自 bundle 的仓库需自行 git remote set-url origin <真实地址>。
  6. GitHub Issues / Pull Requests：不包含。它们存储在 GitHub 的数据库而非 Git 对象库，任何 Git 层面的传输（push、bundle、patch）都不会带走；需要迁移时应使用 GitHub 的导出工具。
  7. 是否适合长期备份：适合作为定期全量备份——git bundle create backup.bundle --all 产出的单文件可离线存放、可随时 clone 复活整个仓库。但要注意：bundle 只含 refs 可达对象（悬空提交、被删分支、refs/stash 这类特殊 ref 之外的状态不保证）；增量 bundle 链必须按序保存、一个不缺，且依赖 SHA 永不改变。稳妥策略是"增量日常 + 每隔一段时间一个独立完整的全量点"。
