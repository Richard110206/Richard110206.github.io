之前这篇博客写的是 Django 官方教程的 Polls 笔记，但感觉就是文档搬运，整个页面也比较简单，很难建全对整个Django项目架构的理解，因而还是找到了我们的老朋友 Tech With Tim，参考里面 Django FULL Project Build - YouTube Clone 的项目，复刻一个Youtube的基本功能！

一、项目是什么

一个仿 YouTube 的视频平台，核心功能：

功能 说明
用户注册/登录 自定义注册表单，注册后自动登录
视频上传 支持 MP4/WebM/MOV/AVI，最大 100MB
HLS 流式播放 通过 hls.js 实现 240p~1080p 多清晰度自适应
点赞/踩 切换式投票系统
观看计数 每次查看自动 +1
频道页 查看某用户的所有视频
删除视频 只能删除自己的视频
暗色 UI 纯 CSS 实现的暗色主题

技术栈：Python 3.13 + Django 6.0 + SQLite + ImageKit.io（云端视频存储/HLS 转码）+ hls.js（前端播放）

项目结构：

核心理解：Django 项目 = 一个「项目配置」+ 多个「应用（app）」。每个 app 是一个独立的功能模块。这个项目有两个 app：accounts（用户认证）和 videos（视频功能）。

数据库配置

为什么 Django 默认用 SQLite？

SQLite 是一个「嵌入式数据库」，整个数据库就是一个文件，不需要单独安装数据库服务。开发阶段用它就够了，但 SQLite 不支持高并发写入，生产环境通常切换到 PostgreSQL 或 MySQL。

切换数据库时注意：

  1. 安装对应的 Python 驱动（mysqlclient / psycopg2-binary）
  2. 在 MySQL/PostgreSQL 中手动创建数据库：CREATE DATABASE youtube_clone;
  3. 重新执行 makemigrations 和 migrate（迁移文件可以复用，不需要修改）
  4. 三种数据库的 ORM 代码完全一致，Django 帮你屏蔽了 SQL 差异

国际化与时区

USE_TZ = True 的影响：

  • auto_now_add 和 auto_now 字段存入数据库时都是 UTC 时间
  • 如果改成 USE_TZ = False，时间直接以 TIME_ZONE 为准存入数据库（不推荐，会丢失时区信息）

静态文件配置

STATIC_URL vs STATICFILES_DIRS vs STATIC_ROOT：

  • STATIC_URL：浏览器端访问静态文件的 URL 前缀（如 /static/css/base.css）
  • STATICFILES_DIRS：告诉 Django 去哪些目录找静态文件（开发时用）
  • STATIC_ROOT：python manage.py collectstatic 会把所有静态文件收集到这个目录（生产部署时用，配合 Nginx/Apache 托管）

ForeignKey 外键是关联两张表的核心字段。user = models.ForeignKey(User, ...) 表示每个视频属于一个用户，Django 自动在数据库创建 user_id 列：

blank vs null（两个字段参数容易混淆）：

参数 作用 适用场景
blank=True 表单验证时允许为空（用户可以不填） CharField, TextField 等字符串字段
null=True 数据库层面允许存 NULL 值 IntegerField, DateTimeField 等非字符串字段

字符串字段一般只用 blank=True（空字符串 "" 比 NULL 更好处理），数字/日期字段如果可选则需要 null=True, blank=True。

auto_now_add vs auto_now：

  • auto_now_add=True：只在对象第一次创建时自动设为当前时间，之后不会再变（适合 created_at）
  • auto_now=True：每次调用 save() 时都自动更新为当前时间（适合 updated_at）

你不能手动修改这两个字段的值，Django 会自动处理。

为什么要把 streaming_url 这些放在 Model 的 @property 里？

因为这样在视图和模板里都能直接用 video.streaming_url，逻辑集中在模型层。如果将来换一个视频服务商，只需要改 imagekit_client.py，视图和模板完全不用动。这就是关注点分离。

VideoLike 模型说明

为什么要有 VideoLike 模型？

Video 模型上的 likes/dislikes 只是计数器。要判断当前用户是否已经点过赞，需要查 VideoLike 表。这种设计叫反规范化（denormalization）——计数冗余存储在 Video 上（读得快），具体投票记录存在 VideoLike 上（能判断状态）。

类似的例子：B站的视频播放量也存在视频表上（读得快），但你点赞的记录单独存（能判断你是否点过赞）。

unique_together = ["user", "video"] 是复合唯一约束，数据库层面保证一个用户对一个视频只能有一条投票记录。等价于 SQL：

choices 参数：SmallIntegerField(choices=LIKE_CHOICES) 让 Django Admin 中该字段自动显示为下拉选择框，而不是手动输入数字。LIKE = 1 和 DISLIKE = -1 是类级常量，在视图代码中用 VideoLike.LIKE 引用，避免魔法数字。

get_object_or_404() 的作用：查询数据库，查到返回对象，查不到直接返回 404 页面（而不是抛 500 错误）。它还常用于权限控制：get_object_or_404(Video, id=video_id, user=request.user) — 既查视频又验证所有权，不是自己的视频就返回 404。

update_fields 优化：video.save(update_fields=["views"]) 只生成 UPDATE ... SET views=? WHERE id=?。如果不加 update_fields，Django 会 UPDATE 所有字段（包括没变的），在高并发下可能导致数据冲突。

AJAX 上传流程

传统表单提交 → 浏览器刷新页面 → Django 返回新页面
AJAX 提交（fetch）→ 浏览器不刷新 → Django 返回 JSON → 前端 JS 处理结果

这就是为什么 video_upload 视图里用 JsonResponse 而不是 render。AJAX 请求需要 JSON 格式的响应。

点赞/踩的切换逻辑

video_vote 处理三种投票情况：

当前状态用户操作结果
未投票点赞赞 +1
未投票踩踩 +1
已点赞再点赞赞 -1（取消）
已点赞点踩赞 -1，踩 +1（切换）
已踩点赞踩 -1，赞 +1（切换）
已踩再踩踩 -1（取消）

核心思路：Video 表存冗余计数（读得快），VideoLike 表存具体投票记录（能判断状态）。两者通过 update_fields=["likes", "dislikes"] 保证计数同步。
