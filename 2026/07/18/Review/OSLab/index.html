写在前面：操作系统的设计哲学

操作系统本质上是一门"资源调度"的工程学 —— 在有限的硬件资源上，让多个程序看似独占、互相隔离、且公平共享。

理解下面三个设计原则，OSLab 中所有机制的设计动机就清晰了：

原则一：特权级隔离

x86 CPU 把运行状态分为用户态（Ring 3）和内核态（Ring 0）。用户程序运行在用户态，不能直接执行特权指令、不能直接访问硬件。任何特权操作（I/O、进程管理、内存分配）都必须通过系统调用陷入内核，由内核代为执行。

这是隔离错误和恶意代码的第一道防线 —— 单个程序的崩溃或越权，不会带垮整个系统。

原则二：抽象即间接

操作系统用三层抽象隐藏硬件细节：

  • 进程抽象 —— 每个进程"感觉"自己独占 CPU，实际是分时复用
  • 虚拟内存 —— 每个进程"感觉"自己有完整 4GB 地址空间，实际通过页表映射到物理内存
  • 统一文件接口 —— 所有 I/O 资源（普通文件、设备、管道、socket）都通过 open/read/write/close 操作

抽象的代价是性能，收益是上层代码的简洁与可移植。

原则三：中断驱动

CPU 平时执行用户代码，"事件"发生时跳去处理，处理完返回。事件来源有三类：

  • 硬件中断 —— 键盘、硬盘、定时器等硬件主动通知 CPU
  • 软件中断 —— 程序主动触发（如 int $0x80 触发系统调用）
  • 异常 —— CPU 执行时遇到问题（除零、缺页、非法指令）

整个系统的运转可以抽象为「用户代码 + 中断处理 + 调度」的无限循环。

Lab3 Shell 程序设计

Shell（外壳）这个名字本身就说明它是包在内核外的一层 —— 早期只是命令解释器，后来演变成 命令语言 + 命令解释器 + 程序设计语言 三合一的工具。

它最核心的特点：解释型执行，逐行读取并执行。这跟 C 语言"编译—链接—执行"完全不同 —— shell 脚本不需要编译，跑一行是一行，所以脚本里语法错误可能要等运行到那一行才报错。

Shell 的设计哲学

Shell 把每条命令看作一个"值"：每条命令都有两个产物 —— stdout（可被反引号 / $() 捕获塞回变量）和退出码（可被 $?、if、&&、|| 判断真假）。

Shell 的所有语法特性（$、` `、[ ]、&&、||、return）都是这两个产物的派生。理解这一点，写脚本就是组合这些"命令值"。

Lab4 系统调用

系统调用（System Call）是用户态程序请求内核服务的唯一受控通道。用户程序运行在用户态（Ring 3），不能直接执行特权指令；任何需要 I/O、进程管理、内存分配的操作，都必须通过 int $0x80 软中断陷入内核态（Ring 0），由内核代为执行。

系统调用的本质

是用户态 / 内核态之间的一道"受控检查站" —— 内核借此审计每一次特权操作，限制单个程序的能力边界，保证错误或恶意代码不会带垮整个系统。

Linux 0.11 用 int $0x80 这条指令触发一个软中断。

  • 硬中断：硬件发来的信号
  • 软中断：程序自己故意触发的中断

x86 CPU 有一张表叫 IDT（中断描述符表），共 256 项（0~255），每一项对应一个中断 / 异常的处理地址。

Linux 对 IDT 256 项的分配约定

编号范围用途
0~31CPU 异常（除零、缺页、调试等）
32~47硬件中断（键盘、硬盘、网卡）
128 (0x80)留给系统调用专用

CPU 收到中断后的处理链路：

  1. 从用户态切换到内核态
  2. 根据中断描述符表（IDT）找到 0x80 对应的处理函数 —— 就是 _system_call
  3. _system_call 根据调用号（放在 EAX 寄存器中）查表跳转到对应的内核函数
  4. 内核函数执行完毕后，通过 iret 指令返回用户态

EAX 寄存器一职两用

调用前 EAX 装系统调用号（“我要哪个服务”），调用后装返回值（“服务结果”）。这是 32 位 x86 Linux 的固定约定 —— 一寄存器两用，省了一个传参槽位。

可扩展性的设计根本

新增系统调用不需要改 _system_call 一行代码，只在 sys_call_table 末尾追加函数指针即可 —— 这就是 Linux 系统调用机制能从最初的几十个扩展到今天数百个的根本原因。

返回值处理的小细节：返回值 < 0 表示内核返回了负的错误码（比如 -EINVAL），宏会把它取反存入 errno，再返回 -1。这是 POSIX 系统调用的统一约定 —— 调用者看返回值是不是 -1 决定要不要查 errno。

① 越界检查 —— 防御性编程

cmpl $nr_system_calls-1,%eax 确保调用号在 [0, 87] 范围内。如果用户传个 999 进来，call *_sys_call_table(,%eax,4) 就会跳到表外读野指针，内核直接崩。所以第一步永远是校验，超出范围就跳 bad_sys_call 返回 -ENOSYS。

② 现场保护 —— 切段寄存器是关键

压栈顺序很有讲究：

为什么压这两组？

  • 段寄存器：用户态 ds/es 指向用户数据段（RPL=3），内核要用 ds/es 访问内核数据，必须先换。movl $0x10, %edx; mov %dx, %ds 把 ds 设成 0x10 —— 这是 GDT 中内核数据段的选择子。
  • fs = 0x17 是 Linux 0.11 的特色：内核数据段在 0x10，用户数据段在 0x17（LDT 中）。内核想读用户传来的指针（比如 read(fd, buf, n) 的 buf），必须用 fs 段跨越特权级访问 —— 因为 ds/es 已经指向内核了，用户空间的地址用 ds 是读不到的。
  • 通用寄存器：因为马上要 call C 函数 sys_max(int, int)，C 函数按调用约定从栈上取参数，所以必须把 EBX、ECX、EDX 中的参数压栈。压栈顺序 edx → ecx → ebx 对应 C 的"参数从右到左入栈"约定（sys_max(max1, max2) 中 max2 在高地址、max1 在低地址）。

这是 AT&T 汇编的基址+变址寻址语法，等价于 Intel 语法的 call [sys_call_table + eax*4]。展开看就是：

④ ⑤ 调度与信号 —— 顺便做家务

跳回来后并不立即返回，而是检查：

  • 是否需要重新调度：如果当前进程 state != 0（被阻塞了）或者时间片 counter == 0 用完了，就跳 reschedule → _schedule 让出 CPU。系统调用是进入内核的"自然时机"，顺手做调度，避免额外中断开销。
  • 信号处理：检查 current->signal 位图，如果有信号待处理（比如子进程发来的 SIGCHLD），调用 do_signal()。Linux 把信号投递时机也定在系统调用返回前 —— 所以 read() 卡住时被信号打断会返回 -EINTR。
  • 恢复现场：按入栈的反顺序弹出寄存器，最后 iret 把 CPU 状态、CS、EIP、EFLAGS、SS、ESP 全部恢复到用户态，把 EAX 里的返回值留给用户程序。
一个反直觉点：为什么用寄存器传参而不是栈？

C 函数调用约定是参数从右到左压栈，但系统调用却用寄存器传参（EBX/ECX/EDX）。

为什么不能用栈传参

int $0x80 切到内核态时，CPU 自动切换到内核栈（从 TSS 读取 esp0）。用户栈和内核栈是两段隔离的内存，用户栈上的参数内核根本访问不到。

只有寄存器是"跨特权级能保留"的载体 —— 它们是 CPU 内部的物理资源，不属于任何地址空间，特权级切换时值不丢。

所以 Linux 0.11 系统调用最多 6 个参数（EAX 装调用号，剩 EBX/ECX/EDX/ESI/EDI/EBP），这是 x86 通用寄存器数量的硬限制。

调试技巧：条件断点

直接在 _system_call 设断点会立刻被命中 —— Linux 启动时 init/main.c 自己就调了大量系统调用（fork()、write()、execve() 全是 int $0x80）。

通用解法：把断点改为条件断点 $eax==87，只有 EAX = 87（__NR_max）时才中断。换其他调用号即可定位任意系统调用。

一句话带走

系统调用 = 用户程序通过 int $0x80 主动陷入内核请求服务。调用号在 EAX，参数在 EBX/ECX/EDX，结果回 EAX。整个机制是"特权级切换 + 寄存器传参 + sys_call_table 跳转"的精密组合。

Lab5 调用 fork 函数创建子进程

fork 是 Unix/Linux 最天才的设计之一：一次调用，两次返回。父进程调用一次 fork，进入内核态，出来时变成了两个几乎一模一样的进程 —— 父进程拿到子进程的 PID（>0），子进程拿到 0。

fork 的本质

不是"创建一个空进程"，而是把当前进程整个复制一份 —— 代码、内存、打开的文件、当前执行位置全都一样。这就是为什么子进程能从 fork() 调用处"继续"执行 —— 它的指令指针 EIP 和父进程返回时一模一样。

这就是为什么子进程"从 fork 调用处继续执行" —— 它的 EIP 和父进程返回时一模一样，看起来就像 fork 这个 C 函数刚刚返回了一样。

子进程 fork 返回 0 的真正原因

父子进程返回到同一个 EIP、同样的栈帧，为什么一个拿到 PID 一个拿到 0？秘密在 copy_process 第 125 行：

p->tss.eax 是子进程 TSS（任务状态段）里保存的 EAX 值。等子进程被调度上 CPU 时，硬件会从 TSS 加载寄存器，EAX 就是 0。

而父进程的 EAX 是 fork 系统调用的返回值 —— copy_process 返回 last_pid（子进程 PID），_system_call 把它塞进父进程的 EAX。所以 C 代码里 pid 看到的值就是 EAX 的值。

"两次返回"的全部秘密

同一个返回点，不同的 EAX —— 这就是 fork 看似神奇、实则朴素的实现：父进程 EAX 装子进程 PID，子进程 EAX 被强制设为 0。C 代码看到的"返回值"实际就是 EAX 寄存器的值。

写时复制（COW）—— fork 不真正复制内存

  • 父子进程都只读这页 → 没事，共享就共享
  • 任一方写 → MMU 触发缺页异常 → 内核分配新页、复制内容、把两个页表项都改成可写

Copy-on-Write 的工程价值

COW 是 fork 之所以能"几乎瞬间完成"的关键 —— fork 后子进程通常马上 execve 加载新程序，根本不会写大多数页，真正复制的只有少数。

这种"乐观策略"在系统设计中很常见：先假设不会冲突，冲突了再补救。代价是写时多一次缺页异常，收益是 fork 速度提升几个数量级。

TSS（任务状态段）—— 硬件上下文切换

  • ltr 指令加载某个 TSS 选择子到 TR 寄存器
  • CPU 切换任务时自动从新 TSS 加载所有寄存器，自动把当前寄存器存回旧 TSS

这是 80386 设计的任务切换机制。现代 Linux 改用软件切换（保存/恢复寄存器到内核栈），因为硬件切换在流水线 CPU 上反而更慢，且 TSS 切换不能像软件切换那样细粒度优化。

execve 的本质

不创建新进程，只换程序的"灵魂" —— PID 不变、task_struct 还是同一个、文件描述符还在，但代码段被新程序覆盖，CPU 从新程序入口开始执行。

fork vs execve：分工明确的"双步设计"

  • shell 想执行 ls | grep foo，先 fork，子进程里把 stdout 重定向到管道，再 execve("ls")

  • 这些修改会被 execve 保留下来，成为新程序的"启动配置"

这就是 shell 实现管道、重定向、环境变量传递的根本机制 —— 称为 fork-execve 模式。

反直觉点 1：内核里不能直接 write()

printf 是用户态的库函数，最终走 write() 系统调用进内核。但内核自己不能调 write()。

两个根本原因

  1. 递归地狱 —— write() 自己就是系统调用，触发 int $0x80 进内核。如果内核在执行系统调用时再触发系统调用，会破坏 _system_call 的栈帧和现场保护逻辑
  2. 用户态约定 —— write() 默认操作的是当前进程的 filp[] 数组、当前进程的用户态缓冲区。内核态下"当前进程"的概念模糊，参数传递约定也不一样

所以必须自己写一个 fprintk —— 绕过系统调用入口，直接调用 _sys_write 或 _file_write 这个 C 函数本身。

反直觉点 2：就绪 ≠ 运行

最容易混淆的概念

PCB 里 state == TASK_RUNNING 这个值，同时表示"就绪"和"运行"两个概念。任意时刻只有一个进程在 CPU 上跑（current 指针指向的那个），其他 TASK_RUNNING 状态的都在就绪队列里。

"运行态"是由 current 指针隐式表示的，没有专门的 state 值。

为什么这么设计？性能 —— 加一个 TASK_READY 状态，每次调度都要改两次 state（旧进程 RUNNING→READY，新进程 READY→RUNNING），cache line 频繁失效。

代价：日志记录需要靠位置语义区分就绪和运行 —— 唤醒点记 TS_READY，被 schedule 选中点才记 TS_RUNNING。

Linux 0.11 调度算法 —— counter 反馈机制

counter >> 1 的精妙设计

阻塞进程的 counter 没被消耗（一直在累积），重新计算时 counter/2 保留了之前没用完的时间片。

结果：IO 密集型进程（经常阻塞）counter 会越积越多，优先级变高；CPU 密集型进程（一直跑）counter 用得快，优先级变低。

这是一种自动适应的反馈机制 —— 不需要手动设置优先级，进程的行为模式自己决定调度倾向。IO 密集型优先，因为它们用 CPU 时间短、需要快速响应（如键盘输入）。

Lab10 分配和释放物理页

物理内存管理的核心数据结构是 mm/memory.c:188 的一个字节数组：

每个字节代表一个物理页（4KB），值是引用计数：0 表示空闲，>0 表示被引用的次数。

mem_map 的本质

不是布尔型的"占用 / 空闲"标志，而是引用计数 —— 支持多个进程共享同一物理页（COW、共享内存、文件缓存页全靠它）。

物理内存的三层划分
  • 0 ~ 1MB：留给内核代码、BIOS 数据，不参与分页管理，物理地址 = 线性地址
  • 1MB ~ HIGH_MEMORY：主内存区，所有进程的物理页从这里分
  • HIGH_MEMORY 以上：硬件限制（早期 PC 最多 16MB）
get_free_page —— 反向扫描的智慧

为什么反向扫描？

%4 操作数 "D" (mem_map+PAGING_PAGES-1) 把 EDI 指向 mem_map 的最后一个字节。std 设置方向标志让 scasb 后 EDI 自动递减，扫描方向是从尾到头。

反碎片策略：高地址页先被消耗，低地址页尽量留空。当需要连续多个物理页时，低地址区域更可能保留连续的大块。

get_free_page 第一次被调用时返回的是物理页框号最大的那个 —— 报告里调试时观察到这个现象，原因就是反向扫描。

free_page —— 引用计数减 1，不是置 0

为什么不直接置 0？因为多个进程可能共享同一物理页 —— 这就是 Lab5 讲的 COW 机制：

  • fork 后父子进程共享页，mem_map 引用计数 = 2
  • 父进程写 → 触发缺页 → 内核新分配一页 → 父进程 mem_map 减 1 → 引用计数 = 1
  • 子进程退出 → free_page → 引用计数 = 0 → 页真正回归空闲池
x86 字符串指令 —— rep / scasb / stosl 硬件加速
指令 作用
std DF = 1（方向标志置位），EDI 自动递减
repne scasb 循环比较 AL 与 [EDI]，不等就继续（每次 EDI ±= 1）
rep stosl 循环把 EAX 写入 [EDI]（每次 EDI ±= 4）

这相当于 C 里的 for 循环，但完全在 CPU 微码里执行，比手写循环快得多。Linux 0.11 大量用这种字符串指令做内存操作。

一句话带走

物理内存管理的核心是 mem_map[] 字节数组 —— 每字节代表一个 4KB 物理页，值是引用计数（不是布尔标志）。get_free_page 反向扫描找空闲页（反碎片），free_page 引用计数减 1（支持 COW 共享）。

现代 Linux 几乎不用段机制（段基址全设为 0），所以线性地址 = 逻辑地址的偏移部分。但 Linux 0.11 充分利用段机制做进程隔离，必须老老实实走完两层翻译。

段选择符 —— 16 位的"路标"

DS 寄存器存的是段选择符（16 位）：

DS = 0x0017 二进制是 0000000000010111：

  • Index = 2：在 LDT（TI=1）里找第 3 个段描述符
  • TI = 1：用 LDT（不是 GDT）。每个进程有自己的 LDT
  • RPL = 3：请求特权级 3（用户态），CPU 据此做权限检查
段描述符 —— 8 字节的"段说明书"

GDT/LDT 是段描述符的数组，每项 8 字节。LDT[2]（数据段描述符）的内容是 0x00003fff 0x10c0f300，按位拼出段基址 = 0x10000000。

这就是为什么 ds:0x3004 的线性地址 = 0x10000000 + 0x3004 = 0x10003004。

LDT 怎么找到 —— 套娃式查表

x86 设计要求 LDT 自己也要"被一个段描述符描述"，LDTR 寄存器本质是 GDT 中的一个选择子。

二级页表的精妙

  • 12 位偏移：页大小 4KB = 2^12

双重循环 —— 二级页表的标准遍历

外层 1024 次循环遍历页目录项（PDE），每个有效的 PDE 指向一张页表。内层 1024 次循环遍历那张页表的所有页表项（PTE）。

P 位 —— "在内存中"标志

PDE/PTE 的最低位（bit 0）

是 P（Present）标志：

  • P = 1：该页/页表在物理内存中，可以访问
  • P = 0：不在内存中（被换出到 swap、或未分配）→ 访问会触发缺页异常

P 位是按需调页（demand paging）的基础 —— 操作系统可以把暂时不用的页换出，PTE 的 P 位置 0，访问时触发异常由内核处理。

物理地址直接当指针用 —— 内核恒等映射的便利

page_table_base 是页表的物理地址，但代码直接把它当 C 指针解引用。这在用户态会崩溃，在 Linux 0.11 内核态却可以：

内核段基址 = 0 + 内核恒等映射

→ 物理地址 = 线性地址 = 逻辑地址偏移

所以内核代码里的指针既可以是"逻辑地址"（编译器视角），又可以直接拿物理地址来用。这个特性是 Lab11 讲的恒等映射的具体应用。

用户态没有这个特权 —— 用户段基址 = nr * 0x4000000，且没有恒等映射。

PDE 是 32 位，低 12 位是属性位（P、R/W、U/S、A、D 等），高 20 位才是页表地址。因为页表必须页对齐（4KB 边界），低 12 位总是 0，可以腾出来存属性。

Lab14 页面置换算法

物理内存有限，进程访问的虚拟页远多于物理页时，内核必须把暂时不用的页换出（swap out）到硬盘 —— 这就是页面置换。Lab14 用 Windows 控制台程序模拟这个算法，重点对比 OPT、FIFO、LRU、LFU、CLOCK 五种策略。

五种算法的本质对比
算法 决策依据 优点 缺点
OPT 未来最远才用 理论最优 无法预知未来，仅作基准
FIFO 进入内存的顺序 实现最简单 Belady 异常，性能差
LRU 过去最久未访问 接近 OPT 实现开销大（时间戳或链表）
LFU 过去访问次数少 适合热点数据 历史包袱（旧热点清不掉）
CLOCK 引用位近似 LRU 硬件友好，快 LRU 的粗糙近似
OPT —— 淘汰"未来最远才用"的页

OPT 无法实现

因为操作系统不可能知道未来访问序列。它的价值是作为理论上限 —— 评估其他算法时，用 OPT 的缺页率作为基准，看你的算法离最优还差多少。

FIFO —— 最简单但有 Belady 异常

FIFO 就一个指针 ReplaceIndex，每次缺页换出最早进来的页。

Belady 异常

FIFO 算法有个反直觉现象 —— 增加物理块数反而可能让缺页率上升。比如引用串 1,2,3,4,1,2,5,1,2,3,4,5：

  • 3 个物理块：缺页 9 次
  • 4 个物理块：缺页 10 次（更多！）

这是因为 FIFO 没考虑局部性 —— 最早进来的页可能正是马上要用的。LRU 和 OPT 不会有 Belady 异常（它们属于"栈算法"）。

LRU —— 看过去，淘汰最久未访问

局部性原理 —— LRU 有效的基础

  • 时间局部性：刚访问过的数据，短期内很可能再次访问（循环、计数器）
  • 空间局部性：访问某地址后，很可能访问其邻近地址（数组、指令顺序执行）

LRU 利用了时间局部性 —— 保留最近访问的页，淘汰老的。这就是为什么 LRU 的实际表现接近 OPT。

CLOCK —— LRU 的硬件友好近似

CLOCK 算法（也叫"第二次机会"）：

  1. 所有页组织成循环链表，指针指向"下一个候选淘汰页"
  2. 每页有 1 位引用位（R），硬件在页被访问时自动置 1
  3. 缺页时，从指针位置开始扫描：
    • R = 1：清零 R，给"第二次机会"，指针前进
    • R = 0：淘汰这一页

CLOCK 的工程价值

只用 1 位就近似实现了 LRU，硬件成本极低 —— x86 页表项的 A 位（Accessed）就是给这个用的。

Linux 内核不用精确 LRU，而是用 Active/Inactive 链表 + 第二次机会（类似 CLOCK），因为它够好且开销低。

同引用串下的缺页率对比

实验引用串 {7,0,1,2,0,3,0,4,2,3,0,1,1,7,0,1,0,3}，结果大致：

算法 缺页次数 缺页率
OPT 7 0.389
LRU 8 0.444
FIFO 10 0.556

OPT < LRU < FIFO —— LRU 只比 OPT 多 1 次缺页，证明局部性原理在实战中确实有效。

一句话带走

页面置换 = 物理内存不够时，按某种策略把页换到硬盘。OPT 是理论上限（无法实现），LRU 是工程最优（基于局部性），CLOCK 是硬件友好的 LRU 近似。FIFO 有 Belady 异常（加内存反而更糟），生产环境不用。

边界标识法（Boundary Tag）是 C 的 malloc / free 怎么实现的一种方案 —— 每个内存块在头部和尾部都加边界标识，让 O(1) 时间找到邻居块、合并空闲块。

核心数据结构

一个字节数组 mem_map[] 管物理页（Lab10），但 malloc 要管任意大小的字节块。边界标识法是字节级内存管理的基础方案。

内存块的结构 —— 头部 + 尾部双重标识

为什么要"双重标识"？

  • 头部的 preLink/nextLink 让空闲块组成双向链表，O(1) 删除任意节点
  • 尾部的 upLink 让给一个块的尾部，O(1) 找到它的头部 —— 这是回收时检查"左邻居"的关键
  • 头尾都有 tag —— 给一个块的任意一端，O(1) 判断它和邻居是不是空闲
分配算法 —— 首次适应
三种分配策略对比
策略 找块规则 优点 缺点
首次适应 第一个够大的 速度快 低地址容易聚集小碎片
循环首次适应 从上次位置继续找（绕一圈） 分配均匀，速度快 可能缺少大块连续空间
最佳适应 找最小的且够大的 大块保留完整 慢（要遍历完），小碎片多
回收算法 —— 四种合并情况

怎么找左右邻居？

  • 右邻居的头：FOOT_LOC(p) + 1（当前块尾部的下一字节就是右邻居的头）
  • 左邻居的尾：p - 1（当前块头部的前一字节就是左邻居的尾）
  • 知道左邻居的尾，通过 upLink 找到左邻居的头

这就是边界标识法的威力 —— O(1) 时间定位邻居，O(1) 时间合并。

合并右块的常见 bug

  1. 漏算头部：合并时只算 p->size + right->size，忘了右块还有头部和尾部的开销（共 +2 个 struct Bound），导致后续访问越界
  2. 顺序错误：先合并指针，再摘除链表节点，导致链表节点指向已经被覆盖的内存

边界标识法的代码看起来直观，但每一步指针操作都涉及多个字段，很容易漏一个。

一句话带走

边界标识法 = 每个内存块头尾都有标识符，构成双向链表。分配用首次适应，回收检查左右邻居的 tag 决定合并策略（4 种情况）。O(1) 找邻居，O(1) 合并 —— 这是现代 malloc 的基础思想。

Lab16 动态内存分配——伙伴系统

边界标识法用双向链表管任意大小的块，灵活但容易碎片。伙伴系统换思路：所有块大小必须是 2 的幂，用规则化结构换取高效合并。

伙伴系统的天才设计

通过限制块大小为 2 的幂（1, 2, 4, 8, 16, … 字节），用异或运算 O(1) 找到伙伴地址 —— 不需要边界标识，靠地址本身的数学结构。

核心数据结构 —— FreeList 数组

FreeList 是 M+1 个链表的数组，第 k 个链表专门装大小为 2^k 的空闲块。

伙伴的概念 —— 用异或算地址

为什么？因为伙伴是父块对半切出来的，两者的地址只在第 k 位不同（k = log2(size)）。

回收算法 —— 递归合并到不能合并

伙伴系统的优势

只要伙伴是空闲的就一路合并，所以永远不会产生外部碎片 —— 释放后能合并的都合并了。

内部碎片 —— 伙伴系统的代价
请求 分配 浪费 利用率
1B 2B 1B 50%
5B 8B 3B 62.5%
17B 32B 15B 53%
65B 128B 63B 51%

伙伴系统的代价

最坏情况：请求 2^k + 1 字节，分配 2^(k+1) 字节，利用率不到 50%。

伙伴系统用最多 50% 的内部碎片换零外部碎片 + 快速合并。对内核级别的页分配这是划算的，对小对象（几十字节）的 malloc 就不划算。

Linux 内核至今仍是主力

MAX_ORDER = 11，意味着一个 zone 内最大支持 2^10 = 1024 页 = 4MB 的连续分配。

Linux 坚持用伙伴系统的原因

  1. 物理页本来就是 4KB 整数倍，2 的幂大小天然契合
  2. 能快速分配大块连续物理内存（DMA、网络缓冲需要）
  3. 合并算法 O(1) + 简单，是热路径性能保证

现代 glibc 的 malloc 用分层策略：小对象用 fastbin，大对象用边界标识法，超大对象用 mmap。内核用伙伴系统，用户态 malloc 在伙伴系统之上 —— 没有一刀切的银弹。

一句话带走

伙伴系统 = 所有块大小必须是 2 的幂。伙伴地址用 addr XOR size 直接算出（不需要边界标识）。释放时递归合并到不能合并，零外部碎片，代价是最多 50% 内部碎片。Linux 内核至今用它管物理页。

Lab17 字符显示的控制

按 A 键屏幕上显示 “a” —— 看起来天经地义，背后其实经过了 键盘硬件 → 中断 → 内核队列 → 显存 一整条流水线。Lab17 就是把这个流水线彻底拆开。

tty 的三队列架构 —— 字符流的三个驿站

为什么分三个队列？

因为生产者和消费者速度不一样 —— 键盘输入可能瞬间多个键，应用还没读；应用 write 也可能比屏幕刷新快。三队列分层缓冲，中间还能做字符处理（行编辑、Ctrl 组合）。

键盘中断处理 —— 从硬件到 ASCII 的完整旅程
扫描码 vs ASCII —— 硬件和软件的分层

A 键的扫描码是 0x1E，但 ASCII ‘a’ 是 0x61。键盘不知道你按的是大写还是小写 —— 它只报告"按下了 0x1E 这个键"，大小写转换由内核做（看 Shift 状态、CapsLock 状态）。

显存 —— 字符显示的最终归宿

属性字节低 4 位是前景色，高 4 位是背景色 + 闪烁位。0x07 = 黑底白字。

终端文字"瞬间出现"的真相

con_write 的工作就是：从 write_q 取字符，按位置写入 0xB8000 起的显存。CPU 写完，显示器下一个刷新周期就能看到 —— 没有"画图"过程，显存就是屏幕。

Lab17 的实验：F12 切换字符替换

实验要求：按 F12 让屏幕上所有字母数字变成 *，再按一次恢复。

钩子点选择的工程价值

为什么钩子加在 copy_to_cooked 和 con_write？因为这两个地方是字符流的"汇聚点" —— 所有键盘输入都会经过前者，所有输出都会经过后者。

好的钩子点要在唯一汇聚处 —— 不会漏掉某些路径。这是流水线设计的额外好处：便于审计和扩展。

同样的机制是真实系统的关键功能：

  • 密码输入：终端关 echo，密码不显示
  • 行模式 vs 原始模式：行模式下回车才送数据，原始模式每个键立即送
  • Tab 补全：拦截 Tab 键，触发补全逻辑
  • Ctrl+C 中断：拦截 Ctrl+C，发送 SIGINT 信号

一句话带走

按 A 显示 a 的完整链路：键盘硬件 → IRQ 1 中断 → keyboard_interrupt 读扫描码 → key_map 转 ASCII → 进 read_q → copy_to_cooked 进 secondary → 唤醒 Shell → Shell read 拿字符 → write 进 write_q → con_write 写显存 0xB8000 → 屏幕显示。三队列（read_q / secondary / write_q）分层缓冲。

Lab18 实现贪吃蛇游戏

Lab17 在字符流水线上加钩子改字符显示，Lab18 把这个思路推到极致 —— 在内核里直接写一个游戏。贪吃蛇从屏幕左上角出发，按 WASD 控制方向，吃食物长大，撞自己就死。

实验的综合价值

一个不到 200 行的内核态游戏，串联了 OS 课程的全部内容：中断系统、进程调度、tty 队列、显存管理、时钟中断、全局变量。这就是为什么很多 OS 课程把它作为期末综合实验。

键盘输入异步通知游戏 —— 生产者-消费者

游戏用两个全局变量驱动整个状态机。键盘中断异步修改它们，游戏主循环每一步读取最新值决定方向。

按键 设置值 含义
‘q’ fflag = 1 启动游戏
‘w’ fflag = 2 蛇 1 向上
‘s’ fflag = 3 蛇 1 向下
‘a’ fflag = 4 蛇 1 向左
‘d’ fflag = 5 蛇 1 向右

事件驱动游戏架构的最简版

键盘是异步事件源，游戏循环是同步消费者。游戏循环每帧（一次 snake_delay 周期）检查一次方向标志，应用最新值。

现代游戏用 SDL、GLFW 监听事件 → 写入事件队列，主循环每帧从队列取事件，更新游戏状态。Lab18 把队列简化成单个变量，但思路完全一样。

游戏循环 —— Game Loop 模式

这是所有游戏的标准循环模式，从 Pong（1972）到 Cyberpunk 2077 都是这个结构。

"画图"的本质 —— 直接改显存

没有"画图"过程 —— 写内存就是画图。这就是为什么字符终端能做到几乎零延迟显示。

jiffies —— 内核计时器

jiffies 是个全局变量，每次时钟中断（10ms 一次）+1。

忙等待（busy wait）的代价

游戏循环期间 CPU 100% 占用。while (jiffies < end) 没有让出 CPU，其他进程完全没法运行。

现代内核用 schedule_timeout() 让出 CPU，等定时器到期再唤醒。Linux 0.11 内核态游戏简化处理 —— 反正就是教学，玩一局也就几十秒。

为什么真实系统不会在内核里写游戏？

  1. 稳定性：游戏 bug 会直接 panic 整个系统
  2. 多用户：内核态游戏占用所有用户的资源
  3. 可移植性：每个 OS 都要重新实现
  4. 安全性：游戏代码有内核权限，能读所有数据

正确架构是 用户态游戏 + 内核提供 API（sys_read 读键盘、sys_write 写终端、ioctl 控制终端模式）。这就是 Unix 哲学 —— 内核只提供机制，策略在用户态。

一句话带走

Lab18 = 在内核态写贪吃蛇。用全局变量 fflag 跨中断和循环传递状态，键盘中断异步写、游戏循环每帧读。游戏循环标准模式：读输入 → 擦旧 → 移动 → 画新 → 延时。综合应用了中断、调度、tty、显存、时钟全部子系统。

Lab19 proc 文件系统的实现

/proc 是 Linux 一个特殊的目录：里面的文件不在硬盘上，每次 read 时由内核动态生成。比如 cat /proc/psinfo 显示当前所有进程信息 —— 这些数据来自内核的 task[] 数组，不是磁盘文件。

procfs 的本质

文件接口下的"伪装" —— 用户态看到的是普通文件（open/read/close），内核态实际是动态生成数据。这是 Unix "一切皆文件"哲学的极致体现。

"虚拟文件系统"的实现方式

不是新建一套独立的系统调用，而是在现有的 sys_read 里加分支 —— 每种特殊文件类型有自己的 read 函数。

psread 函数 —— 内核状态的"格式化输出器"
f_pos 文件位置指针 —— 为什么需要它

f_pos 的双重作用

  1. 作为"是否首次调用"的标志：第一次进入 psread 时 f_pos = 0，触发缓冲区生成。后续调用 f_pos != 0，跳过生成步骤，直接从缓冲区拷数据
  2. 记录读取位置：read 后 f_pos += 字节数，下次接着读

put_fs_byte —— 跨用户/内核空间写字节

buf 是用户空间的指针，内核不能直接 buf[i] = ...。必须通过 put_fs_byte 用 fs 段前缀写入 —— 这就是 Lab4 讲的"fs = 0x17 是 Linux 0.11 的特色"的应用。

现代 Linux 的 procfs

Lab19 的 procfs 只是个玩具 —— 单一文件 psinfo，写死格式。现代 Linux 的 /proc 远超想象：

文件 内容
/proc/cpuinfo CPU 信息
/proc/meminfo 内存使用
/proc/loadavg 系统负载
/proc/version 内核版本
/proc/pid/stat 单个进程状态
/proc/pid/maps 进程内存映射
/proc/sys/net/... 可写 —— 调整内核参数

procfs 的设计精髓

把内核数据用文件接口暴露，让所有文件工具都能用 —— 不需要专门的系统调用，不需要新的工具集。

这就是为什么 /dev/null、/dev/zero、/dev/random 都是文件 —— 它们读的内容不同，但接口完全一样。接口复用 是 Unix 哲学的核心。

一句话带走

procfs = 用文件接口暴露内核状态。机制：加新文件类型 S_IFPROC，在 sys_read 里加分支调用 psread。psread 用 f_pos 判断是否首次调用（首次才生成数据），用 put_fs_byte 跨用户/内核空间写字节。Linux 后来发明的 /proc/sys/ 可写文件让用户态能配置内核参数。

分级寻址的工程权衡

  • 小文件（< 7KB）用直接块，访问快
  • 中文件（< 256KB）用一次间接
  • 大文件（< 64MB）用二次间接

如果全用直接块：每文件最多 7KB。如果全用间接块：小文件也要多读一次磁盘，慢 10 倍。分级是速度和灵活性的折衷。

路径解析的开销

文件系统本质的简洁性

再复杂的文件系统，底层都是"用某种结构把磁盘切成块、用某种方式把文件映射到块"。MINIX 1.0 的核心数据结构（超级块 + 位图 + inode + 数据块）30 年没变 —— ext4、XFS、Btrfs、ZFS 都能用这套框架理解，差别只在每个组件的设计选择。
