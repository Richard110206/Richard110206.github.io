问题 A:接口报 think\route\Domain not found

遇到的问题

小程序/网页请求接口时,PHP 抛出 Class not found 错误,提示 think\route\Domain 类找不到,整个接口直接挂掉。

为什么会出现

ThinkPHP 8.1 的 Route.php 第 19 行 use think\route\Domain; 并在多处 new Domain($this) 实例化它。但 vendor/topthink/framework/src/think/route/Domain.php 这个文件在服务器上根本不存在。

知识点盲点

  • vendor 完整性 ≠ 代码上传成功:zip 包解压不完整是常见坑,常见诱因有杀毒软件拦截、中文路径编码错误、zip 截断、FTP/SCP 传输中断。
  • PHP autoload 的脆弱性:Composer 的 autoload 是按需加载,文件不存在时只有真正调用到才会报错,容易在测试阶段漏过去。

如何解决

本地校验过的内容来自 https://raw.githubusercontent.com/top-think/framework/v8.1.1/src/think/route/Domain.php(1285 字节)。

问题 B:接口报 file_put_contents(...): Failed to open stream

遇到的问题

错误路径指向容器内 /www/sites/fuyangjia.top/index/runtime/session/shopxo/sess_xxxxx,经历两个阶段:

  1. No such file or directory → 目录不存在
  2. Permission denied → 目录存在但 PHP 写不进去

为什么会出现

关键背景: 1Panel 用 Docker 跑 PHP-FPM,同一个物理目录有两个视角:

视角路径
宿主机(SSH 直接看到)/opt/1panel/www/sites/fuyangjia.top/index/
容器内(PHP-FPM 看到的)/www/sites/fuyangjia.top/index/

挂载点把这两个路径映射到同一个物理目录。但 UID 不匹配:

位置www-data 的 UID
宿主机 /etc/passwd33
容器内 /etc/passwd1000

PHP-FPM pool 配置写的是 user = www-data,意思是「以容器内的 www-data 跑」→ 实际是 UID 1000。而此前 chown www-data:www-data 给的是宿主机的 www-data → UID 33。同名不同 ID,所以 PHP-FPM 在 UID 1000 下无法写入属于 UID 33 的目录。

知识点盲点

  • Linux UID/GID 是数字,名字只是 /etc/passwd 的映射:容器和宿主机各自有独立的 /etc/passwd,同一个名字 www-data 可以映射到不同的 UID。
  • chown www-data:www-data 在容器化场景下是危险的:因为它取的是当前 shell 所在视角的 passwd 文件。在宿主机执行就拿到宿主机的 UID 33。
  • docker exec php -r 'echo posix_geteuid();' 不能反映 FPM worker 的真实用户:因为 docker exec 默认以 root 跑,得到 uid=0 会误导。FPM worker 的身份只看 pool 配置(/usr/local/etc/php-fpm.d/ 里的 user / group)。

如何解决

问题 C:点击支付报「支付方式有误」

遇到的问题

小程序点击支付时,接口返回 payment_method_error_tips → “支付方式有误”,根本走不到微信收银台。

为什么会出现

app/service/PaymentService.php 的 PaymentData 方法里有一段针对微信小程序环境的过滤逻辑放错了位置:

PaymentData 按 ID 查单个支付方式(返回一维数组),array_filter 在一维数组上遍历每个字段值,isset($item['payment']) 永远 false,过滤后 $data 变成空数组 []。后续 OrderService::Pay 判空就直接报「支付方式有误」。

知识点盲点

  • PHP array_filter 在一维关联数组上的行为:array_filter 会遍历数组的每个 value(此处是字符串、数字等标量字段值),而不是当成「一条记录」。把一维关联数组当成二维列表去 filter,结果是「过滤掉所有不符合结构的字段」,几乎一定会得到空数组。
  • 看函数返回结构再写过滤逻辑:PaymentList 返回二维,PaymentData 返回一维(取 [0]),两者结构不同,过滤策略不能照搬。
  • 重复过滤的代码味道:微信端支付方式筛选已经由 BuyPaymentList 基于 apply_terminal 字段正确处理了,PaymentData 再过滤一次属于职责越界。

如何解决
删除 PaymentData 中(原第 289-297 行)那段错误的 array_filter 过滤。微信端的支付方式筛选已由 BuyPaymentList 处理。

问题 D:点击支付报「目录没有操作权限 […/public/]」

遇到的问题

修完问题 C 后再点支付,接口返回:

授权 public/ 后又出现:

为什么会出现

app/service/PaymentService.php::PowerCheck() 有两道校验,都需要 PHP-FPM(UID 1000)可写:

  1. dir_root_path(API 模式下 = public/) — 用于写入支付入口文件 payment_default_order_weixin_notify.php / _respond.php
  2. payment_dir = extend/payment/ — 支付插件目录

之前的修复(问题 B)只覆盖了 runtime/,所以 public/ 和 extend/payment/ 仍是宿主机默认 owner(UID 33 或 root),容器内 UID 1000 写不进去。

知识点盲点

  • PHP 应用写盘目录不止 runtime/:缓存、日志、session 是显性的,但支付插件入口文件、上传目录、模板编译目录都需要写权限。只授权一部分目录,后续会持续踩坑。
  • 「修一次解决一类」比「修一次解决一个」更省心:与其逐目录 chown,不如整站根目录一次性 chown 给容器内 PHP 用户。
  • sh -lc 不支持 brace expansion:docker exec shopxo-php82 sh -lc '...{a,b,c}...' 不会展开,要么用 bash -lc,要么写成普通 for 循环。

如何解决

问题 E:体验版 wx.requestPayment 报 access denied

遇到的问题

  • 微信开发者工具 → 点支付 → 弹二维码 → 扫码支付 ✅
  • 体验版小程序 → 点支付 → requestPayment:fail access denied ❌

为什么会出现

这是微信侧限制,和服务器代码无关。

场景trade_type是否依赖小程序主体能力是否受备案影响
开发工具「扫码支付」NATIVE否(等同于网页扫码支付)否
体验版 wx.requestPaymentJSAPI是是

该小程序尚未完成工信部备案,微信官方从 2024 年起对未备案小程序限制核心接口,包括微信支付、获取手机号等。所以 JSAPI 调起被微信侧直接拦截,前端表现为 access denied。

知识点盲点

  • 微信小程序备案是硬性门槛:2024 年起工信部要求所有小程序备案,未备案的小程序无法使用微信支付、获取手机号等核心接口。这是合规问题,不是代码问题。
  • NATIVE 与 JSAPI 的本质区别:NATIVE 是网页扫码支付逻辑,不依赖小程序主体能力;JSAPI 必须通过小程序主体调起,受备案约束。
  • 「在开发者工具能用 ≠ 在真机能用」:开发者工具是开发环境,很多限制会被放宽,必须在体验版/正式版回归测试。

如何解决

  1. 等管局备案通过(通常 1–20 个工作日)
  2. 备案通过后,再到 pay.weixin.qq.com →产品中心→AppID 账号管理,关联小程序 AppID 与商户号
  3. 然后到小程序管理后台 →微信支付,确认绑定
  4. 备案期间如要内部测试,继续使用扫码支付路径(开发者工具或 PC 端)

Navicat 远程连接 MySQL 排查实录

环境信息

  • 服务器:101.35.232.52(腾讯云 Debian 13)
  • 目标:本地 Navicat 连接服务器上的 MySQL

问题:Navicat 连接服务器 MySQL 完全失败

遇到的问题

Navicat 连接失败,完全没头绪,无法判断是端口不对、防火墙拦截、还是账号权限问题。

为什么会出现

服务器上的 MySQL 跑在 Docker 容器中,通过 docker-proxy 绑定到 127.0.0.1:3306,只对本机开放,不对公网监听。1Panel 出于安全考虑,把端口映射配置成 127.0.0.1:3306:3306,这是非常合理的安全默认值 —— 数据库不应该直接暴露在公网。

知识点盲点

  1. 端口探测是排查第一步 — Test-NetConnection / telnet 能秒级定位「网络问题还是服务问题」,不要盲目改配置。
  2. ss -tlnp / netstat -tlnp 是核心诊断命令 — 一次看到所有监听端口、监听 IP、对应进程,MySQL 真实端口和绑定地址一目了然。
  3. 看进程名比看端口号更可靠 — 这次差点把 13757(1Panel)误认为 MySQL 端口,通过进程名 1panel-core 立刻识破。
  4. Docker 监听地址的三种含义:
监听地址 含义 外部能否连接
127.0.0.1:3306 只监听宿主机本地回环 ❌ 不能
0.0.0.0:3306 监听宿主机所有网卡(含公网 IP) ✅ 能(若防火墙也放行)
192.168.x.x:3306 只监听内网网卡 ⚠️ 仅内网可连
  1. 完整连接链路上的多重关卡:即使把 Docker 改成 0.0.0.0:3306,外部要连上 MySQL 还得过以下所有关卡:

任意一关失败都会「连不上」,这就是为什么直接暴露公网连接 MySQL 既不安全、调试又麻烦。

如何解决

Step 1:本地端口连通性测试

→ SSH 可用,通过 SSH 进入服务器继续排查。

Step 2:SSH 登录服务器,看 MySQL 真实监听情况
Step 3:对比方案,选 SSH 隧道
方案 优点 缺点 安全性 评价
用 1Panel 面板 Web 操作 简单,一键备份 面板暴露公网有风险 ⚠️ ⭐⭐⭐
Navicat SSH 隧道 零配置改动,加密传输 每次要 SSH 认证 ✅ 高 ⭐⭐⭐⭐⭐ 采用
改 Docker 绑定 0.0.0.0 直连方便 MySQL 暴露公网,易被爆破 ❌ 低 不推荐

首页「共创专享」楼层商品顺序调整

问题:商品顺序与设计稿不一致,且 sort_level 改了不生效

遇到的问题

需要把首页「共创专享」楼层内 3 个商品的第 1 个(共创专享)与第 3 个(家庭健康套餐)位置互换。

修改前修改后
① 共创专享(id=3)① 家庭健康套餐(id=1)
② 熔融盐草本漱口水(id=2)② 熔融盐草本漱口水(id=2)
③ 家庭健康套餐(id=1)③ 共创专享(id=3)

直觉做法是去后台改 sort_level,但改了不生效。

为什么会出现

前端 pages/index/index.vue 仅渲染后端返回的 data_list[*].goods,顺序完全由后端决定。后端排序逻辑在 app/service/GoodsService.php 的 HomeFloorList 方法:

  • 排序字段由后台配置 home_index_floor_goods_order_by_type 决定(当前是「最新」,即 g.id DESC),不读 sort_level。
  • 商品表 sxo_goods 中三个商品 id=1/2/3,按 id DESC 排出来就是 [3, 2, 1],正好是修改前的顺序。

知识点盲点

  • 「前端只渲染」 ≠ 「前端能控制顺序」:小程序前端的列表渲染顺序 = 后端给什么顺序就显示什么顺序,改前端没有任何意义。
  • 后台「排序字段」配置决定 SQL order by:看到 order by type 这种配置项,要先去代码里看它实际映射到哪个字段,不要凭字段名猜。
  • sort_level 是商品级配置,但只有当 order by 选了它时才生效:很多 CMS / 电商系统都有这种「字段存在但默认不启用」的坑。
  • 改全局配置会牵一发动全身:改后台 rule 会同时反转其他 5 个楼层,最小爆炸半径的做法是在 PHP 层加定向特判。

如何解决

唯一改动点:app/service/GoodsService.php 的 HomeFloorList 方法内,第二次循环给 $cv['goods'] 赋值之后(原文件 L247 后):

说明:

  • $cv['id'] == 1 — 只对「共创专享」楼层生效,其他楼层不受影响。
  • count($cv['goods']) >= 3 — 守卫条件,商品数少于 3 时不处理(避免未来商品下架后出现意外)。
  • array_reverse + array_values — 反转顺序并重建索引。

缓存与生效

HomeFloorList 内部带 180 秒缓存(MyCache($key, $data, 180)),Index 接口层还有一层缓存。改完代码部署后,最长 3 分钟内自动生效;若需要立即生效,可在 1Panel 后台清理 ShopXO 缓存或重启 PHP 容器。
