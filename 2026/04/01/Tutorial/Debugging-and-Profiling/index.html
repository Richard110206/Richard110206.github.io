Debugging and Profiling

A golden rule in programming is that code does not do what you expect it to do, but what you tell it to do.

  程序出 bug 是日常，而调试和性能分析就是定位问题与优化程序的两种核心手段：前者解决"程序为什么不对"，后者解决"程序为什么慢/为什么吃内存"。本篇参考 MIT Missing Semester — Debugging and Profiling 的脉络，整理从打印调试、调试器、专用工具到性能分析的完整工具链，以 C/C++ 在类 Unix 系统下的实践为主。

本篇组织：第一章是日志与打印调试 → 第二章是调试器 LLDB/GDB → 第三章是专用工具（系统调用追踪、网络抓包、Sanitizers、Core Dump、静态分析）→ 第四章是性能分析（CPU / 内存 / 火焰图）→ 第五章是资源监控。

一、调试的前置准备：日志与打印

  当我们遇到问题时，最朴素也最有效的两种手段是：

  • 在适当的地方添加 printf / cout 打印语句
  • 使用程序中的日志记录（logging）

  相较于裸打印，日志库的优势在于：

  • 能定向到不同的输出位置（控制台、文件、远程日志服务器）
  • 能设置严重程度级别（INFO、DEBUG、WARN、ERROR、FATAL），并按级别过滤输出
  • 支持对日志进行结构化记录（如 JSON），便于日后检索与统计
  • 可以通过配置文件动态开关，不需要重新编译

常见的 C++ 日志库：spdlog、glog、log4cpp；Python 中则使用内置 logging 模块。

调试策略：日志只能告诉我们"程序做了什么"。当问题无法稳定复现（如只在生产环境偶发）时，优先在关键路径上加上 DEBUG 级别的日志，下次出现时才有线索可查——这是 Missing Semester 反复强调的做法。

  但日志只能告诉我们"程序做了什么"，要观察"程序正在做什么"——尤其是定位崩溃位置、检查变量值、跟踪调用栈——就需要调试器（Debugger）。

二、调试器：LLDB / GDB

  调试器允许我们在程序执行时与之交互，主要能力包括：

  • 在到达某一行时停止执行（断点）
  • 逐条执行单个指令（单步）
  • 检查、修改变量的值
  • 查看调用栈（backtrace）
  • 满足条件时停止执行（条件断点）

（一）编译时带调试信息

  如果我们修改了源程序，必须退出 LLDB/GDB，重新编译一次程序再进行调试——原窗口里运行的是旧的二进制文件，无法直接用于新版本的程序。

  • -g：核心调试参数，向可执行文件中嵌入调试信息（行号、变量名、函数名等）。没有它，LLDB/GDB 无法定位源码位置；
  • -O0：关闭优化。开启优化（-O2、-O3）后，变量可能被优化掉、语句顺序被打乱，调试时会出现"变量值不可用""单步乱跳"等现象；
  • -o account_debug：指定输出文件名（省略则默认 a.out）；
  • debug.cpp：待编译的源文件。

开启 -O2 及以上优化时，编译器可能：

  1. 把变量直接放进寄存器，导致 print 显示 <optimized out>；
  2. 内联函数或重排指令，导致单步执行顺序与源码不一致。

调试时建议始终使用 -O0 -g。

（二）启动调试器

  由于我使用的是 macOS，这里用系统自带的 LLDB 演示（Linux 下用 GDB，命令大致相同，文末附有对照表）。

（三）基础流程：运行、断点、继续

  • run（简写 r）：从 main 函数开始重新启动程序
    • 没有断点：完整运行到底
    • 有断点：运行到断点停止
  • breakpoint set --file debug.cpp --line 25（简写 b debug.cpp:25）：在指定文件的某行设断点
  • continue（简写 c）：从暂停处"一直运行"，直到遇到下一个暂停条件（断点 / 程序结束 / 崩溃）

（四）查看变量与表达式

  • frame variable（简写 fr v）：打印当前栈帧中所有可见变量的完整值
  • print <expr>（简写 p）：打印单个表达式（可调用函数、做运算）
  • expression <expr>（简写 expr / e）：修改变量值，用于在不重启程序的前提下尝试不同的输入

修改内存中的值后无需重编译——这正是调试器最强大的地方。可以快速验证"如果把 balance 改成 0，程序会走哪个分支"。

（五）单步执行

命令 简写 含义
step s 单步进入：执行一行，若是函数调用则进入函数体
next n 单步跳过：执行一行，把函数调用整体当作一步
finish f 单步跳出：执行到当前函数返回
until <line> u 执行到指定行（常用于跳出循环）
stepi si 单条机器指令（汇编级）
nexti ni 同上，但跳过 call 指令

记忆口诀：step = 进入函数（深入）；next = 跳过函数（横向）；finish = 跳出函数（返回）。

（六）调用栈

  • thread backtrace（简写 bt）：打印当前线程的调用栈，定位崩溃点必备
  • frame select 2（简写 f 2）：切换到第 2 号栈帧
  • up / down：向栈底 / 栈顶移动一帧

（七）断点管理

  • breakpoint list（简写 br l）：查看所有已设置的断点
  • breakpoint delete 1（简写 br del 1）：移除编号为 1 的断点
  • breakpoint disable 1 / breakpoint enable 1：临时禁用 / 启用，不删除

三、专用调试工具

  调试器解决"逻辑错误"，但有些问题——内存越界、用后释放、竞态条件——光靠断点很难复现。下面是几类专门工具：

（一）系统调用追踪：strace / ltrace / dtrace

  当程序行为异常但又看不出哪儿错时，先看看它对系统做了什么——打开了哪些文件、连接了哪个地址、读了什么：

strace 的常用参数：

  • -f：追踪子进程
  • -e trace=...：只看某类调用（open、network、file 等）
  • -p PID：附着到正在运行的进程
  • -c：统计每个调用的次数和耗时
  • -y：把 fd 显示为对应文件路径

（二）网络抓包：tcpdump / Wireshark

  “为什么连不上服务器”“为什么对方收不到我的包”——这类问题最直接的办法是抓包：

tcpdump 不解析协议、不显示包内容；想看 HTTP / TLS 报文细节，把数据导成 .pcap 后用 Wireshark 打开。

（三）Valgrind：内存错误检测

  Valgrind 是 Linux 上的内存调试神器，能在不重编译程序的情况下检查：

  • 读写未初始化内存
  • 读写已释放内存（use-after-free）
  • 内存泄漏（definitely lost / indirectly lost）
  • 非法读写（heap buffer overflow）

（四）Sanitizers：编译期注入的轻量检查

  由 GCC/Clang 内置，比 Valgrind 快一个数量级（仅 2x 左右减速），是现代 C/C++ 项目的主流选择：

工具 编译参数 检测内容
AddressSanitizer -fsanitize=address 堆/栈/全局越界、use-after-free、double-free
UndefinedBehaviorSanitizer -fsanitize=undefined 整数溢出、空指针解引用、除零等
ThreadSanitizer -fsanitize=thread 数据竞争（data race）
MemorySanitizer -fsanitize=memory 读取未初始化内存
LeakSanitizer -fsanitize=leak 内存泄漏（通常随 ASan 一起启用）

（五）Core Dump：崩溃后的事后分析

  程序崩溃时，操作系统可以把当时的内存映像写到磁盘（core 文件），再用调试器加载分析：

生产环境必备：守护进程崩溃后通常不会停在原地等待调试。开 core dump 后，每次崩溃都会留下"现场快照"，事后用 bt 一目了然。

（六）静态分析：在运行前就发现问题

  调试器是运行时工具，但很多 bug 不用跑就能发现——这是静态分析的舞台：

语言 工具 用途
C / C++ clang-tidy、cppcheck 未初始化变量、内存泄漏、风格问题
C / C++ clang --analyze 编译器级别的静态检查
Python pyflakes、pylint 未使用变量、导入错误
Python mypy 类型检查
Shell shellcheck shell 脚本反模式
Rust cargo clippy Rust 官方 lint

Missing Semester 的建议：把静态分析集成进编辑器（保存即跑）和 CI（PR 检查），可以消灭一大类低级错误，调试器留给那些静态分析抓不到的逻辑问题。

四、性能分析 Profiling

  调试解决正确性问题，性能分析解决效率问题。Profiling 的核心目标是回答两个问题：

  1. 时间都花在哪了？ → CPU profiling
  2. 内存都被谁占了？ → Memory / heap profiling

不要凭直觉优化：人类对程序性能的直觉非常差。先用 profiler 找出真正的热点，再动手——否则你大概率优化了一个无关紧要的地方。Missing Semester 给出的真实例子：程序员以为瓶颈是网络，profiler 一看，时间花在编译正则上。

火焰图（FlameGraph）

  perf report 是文本，调用层级深时不好读。火焰图把采样结果画成一张横向柱状图：每行是一个栈，柱子越宽代表这个函数占用 CPU 越多。

打开 flame.svg（浏览器即可），鼠标悬停能看到函数名 + 采样占比，点击可放大某一子树。

macOS 上对应工具是 Instruments（Xcode 自带），其中的 Time Profiler 模板与 perf record 等价，并自带可视化调用树。

heaptrack 会列出：

（四）性能分析的一般流程

  拿到一份 profiling 数据后，建议遵循 Measure → Locate → Hypothesize → Fix → Re-measure 的循环：

  1. 先测，不要猜：用 time / perf stat 确认程序到底是 CPU-bound 还是 I/O-bound；
  2. 找热点：用 perf record 或火焰图找出占比 top-3 的函数；
  3. 形成假设：为什么这个函数慢？算法复杂度？缓存不友好？锁竞争？
  4. 改一处再测一处：每次只改一个变量，重新采样对比；
  5. 检查回归：优化后跑完整测试集，避免引入正确性问题。

两条常见反模式：

  • 过早优化：在没测量之前凭直觉改代码，常常优化了无关紧要的地方；
  • 微优化：在 99% 时间都不在的函数里抠一行汇编，不如先重构数据结构。

五、资源监控

  调试和性能分析之外，日常还需要实时观察系统状态——CPU 占用、内存、磁盘 I/O、网络。Missing Semester 推荐这几个工具：

工具 用途
top / htop 实时进程列表，按 CPU/内存排序（htop 彩色更直观）
iotop 哪个进程在读写磁盘
iftop / nethogs 网络流量按进程 / 按连接
dstat / vmstat 综合 CPU/磁盘/网络/内存
glances 一站式系统监控（curses + Web UI）
netstat / ss 当前网络连接、监听端口

定位"线上卡顿"的标准动作：先 htop 看是不是某进程占满 CPU → 不行就 iotop 看是不是磁盘 I/O 撑满 → 再不行就 ss / iftop 看是不是网络阻塞。一套下来通常就能锁定瓶颈。
